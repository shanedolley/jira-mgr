# Desktop App

The Electron app, package `@jira-mgr/desktop`, built with electron-vite. The renderer lives here too: React, Tailwind and TanStack Query. Today it logs in, then shows a sidebar with the saved views and the Tree: the project's issues grouped by Customer, Epic and child, with a toolbar of toggles and filters, `J` and `K` navigation, and a space-bar Peek that edits the summary in place. Enter opens an issue's full page, with a properties sidebar of pickers. `C` opens a create modal, and a Delete button on the Peek and the page opens a confirmation that lists the subtasks it deletes. `Cmd+K` searches the loaded issues, `S`, `A`, `L`, `P` and `E` open the active issue's pickers and summary editor, and `Cmd+Z` undoes the last field edit. Light or dark theme.

## Run

```
pnpm dev     # app with hot reload
pnpm build   # writes apps/desktop/out
pnpm test    # Vitest: IPC validation, backend loads and views, tree model, optimistic updates, queries
```

`pnpm package` (from the repository root) builds the app and assembles the unsigned `dist/jira-mgr.app`. [Install the Desktop App](../../docs/how-to/install-desktop-app.md) covers installing it.

`pnpm dev` and a normal launch read and write the real state folder and Keychain item. Set `JM_STATE_DIR` to a scratch folder for any manual run that must not touch them.

src/main/       main process: window, IPC handlers, the backend that calls core
src/preload/    preload script: the only bridge to the renderer

## Tree

- Loading: `['issues', 'unresolved']`, `['toggles']` and `['me']` start together. The Tree renders once the unresolved phase and the toggles have data, and `me` when "Assignee: me" or the assignee filter needs it. `['issues', 'done']` then loads in the background, always, since Done chips need the Done issues under open parents, and the toolbar shows the running count. An edit reads only the edited issue again and leaves both phase loads alone.
- The Tree has no grouping, sorting or Done rules of its own: `buildHierarchy` and `issueMatcher` from core decide, as `jm issue tree` does. One difference remains. `jm issue tree` never loads Done issues under "Hide done", so it prints an open Story whose Epic is Done under No Epic. The app moves that Story under its dimmed Epic once Done issues load.
- Rows are 32 pixels tall and only the rows in view, plus 10 of overscan and the active row, are in the DOM. Scroll anchoring keeps the first visible row where it is when a rebuild changes the rows above it.
- Collapsed groups, revealed chips and filters last for the session. "Hide done", "Assignee: me" and "Hide empty Customers" persist in `settings.json` under `toggles`; the CLI ignores them.
- Keys: `J`/`K` and the arrows move, `ArrowRight` and `ArrowLeft` expand, collapse and change level, `Shift` with them expands or collapses all, `Home`, `End`, `PageUp` and `PageDown` jump, `Enter` toggles a group or opens an issue's full page, `Space` toggles the Peek, `Esc` closes it. The single-letter keys and `Cmd+K`, `Cmd+Z` and the global `Esc` are in Keyboard below.

## Issue Page

- Enter on an issue row, or Open in the Peek, shows the page over the Tree. The Tree stays mounted and inert under it, so its scroll position, active row and Peek survive. Esc or Back to issues returns to the Tree, with focus on it. The parent key and the subtasks open their own pages.
- The page shows the issue from the loaded lists at once, then reads it on its own (`issues:get`), which adds the description and subtasks. The description is read-only Markdown text until the editor in D4.
- The sidebar lists Status, Assignee, Priority and Labels; Type, Parent, Customer, Engagement and Sprint; Start date, Due date, the original estimate, the remaining estimate (read-only) and Time remaining (h). `propertyRules` in core hides Sprint, Parent and the estimates on an Epic, hides Sprint on a Subtask (Q20), and fixes the type of anything but a Story, Task or Bug. Time remaining (h) shows on a Task, Bug and Subtask as well as a Story, which is wider than Q22's "Story only", because live edits accepted it on a Subtask.
- Every picker is a `Picker`: a button that opens a native popover holding a listbox. With a search field the field is a combobox that points at the active option with `aria-activedescendant`; without one the listbox takes focus. Arrow keys move, Enter chooses, Esc closes and returns focus to the button, and ArrowDown on the button opens it.
- Status lists the statuses the issue can reach now (`issues:transitions`), in Q21 order, and moves by target status. Assignee lists Unassigned, Me and the people on the most recently updated loaded issues (up to five), then searches assignable users (`users:search`). Labels are the labels on the loaded issues, which are the project's own, since Jira's suggestions are site-wide (Q35); typing a new one with no spaces creates it. Sprint lists the active sprint and future sprints that have dates, with Show all for the closed and undated ones; a closed sprint is listed disabled, since Jira refuses a move into it (Q20). Customer, Engagement, Priority and Type come from the create metadata (`fields:options`), and Type offers only Story, Task and Bug (Q23).
- Parent searches the loaded issues that can be a parent (`parentCandidates`). When the chosen parent's Customer or Engagement differs, a modal asks whether to also set them to the parent's (Q16) before anything is sent: Move and set, Move only, or Cancel with Esc. One edit carries the parent and, if asked, the Customer and Engagement.
- Dates, the original estimate and Time remaining are fields that save on Enter or when focus leaves them, and revert on Esc. A date input steps through its day, month and year segments on Tab, so Enter or leaving the field saves. The original estimate takes a Jira duration such as `2h 30m`; anything else shows an error and sends nothing.
- Every edit is optimistic, and an accepted one goes on the undo stack (see Keyboard). A refused edit puts back only the fields it changed, and only while they still show the optimistic value, and the sidebar says why. Once the last edit to an issue settles, the app reads that one issue again and the lists and the page take what Jira holds, including what Jira changed itself: an estimate edit also moves the remaining estimate and Time remaining. No list is reloaded for an edit. A status change that crosses into or out of Done moves the issue between the two cached lists.
- The "Match Epic's Customer" button in the Peek and on the page copies the Epic's Customer onto a child whose own differs (Q15). An Epic with no Customer offers no fix, since core cannot clear the field.

## Keyboard

One `keydown` listener on the document, in the Shell, asks `resolveKey` (`keymap.ts`) what a keystroke means. The Tree's own keys (`J`, `K`, arrows, `Space`, `Enter`) stay on the Tree element, and the page's `Esc` stays on the page, so both have run, and called `preventDefault` when they acted, before the listener sees the event; it skips a handled event.

| Key     | Does                                                                                                                                                   | Source  |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------- |
| `Cmd+K` | Opens the palette over the loaded issues                                                                                                               | Q5, Q37 |
| `C`     | Opens the create modal                                                                                                                                 | Q5      |
| `S`     | Opens the Status picker                                                                                                                                | Q5      |
| `A`     | Opens the Assignee picker                                                                                                                              | Q5      |
| `L`     | Opens the Labels picker                                                                                                                                | Q5      |
| `P`     | Opens the Priority picker                                                                                                                              | Q5, Q31 |
| `E`     | Edits the summary (the "Edit summary" button). Jira has no separate name field and the description editor is D4's, so the summary is what "edit" means | Q5, Q4  |
| `Cmd+Z` | Undoes the last field edit                                                                                                                             | Q38     |
| `Esc`   | Backs out one layer (see Esc below)                                                                                                                    | Q5      |

- **Target.** `S`, `A`, `L`, `P` and `E` act on the open page's issue, else on the active Tree row's issue. A Customer header, a "N done" chip or no active row has no issue, so the key does nothing. Ctrl stands in for Cmd off the Mac.
- **Guard.** A letter is a command only alone: not with Cmd, Ctrl or Alt, not held down, not during IME composition, not already handled, and never when focus is in a text field, picker, dialog, popover, `contenteditable` or an element with the `textbox`, `combobox`, `listbox` or `menu` role (`keepsLetters`). `Cmd+Z` and `Esc` obey the same target rule, so a text field keeps its native undo and a picker keeps its own `Esc`. `Cmd+K` opens from a text field, since it edits nothing there, but not over a dialog or an open picker.
- **Pickers from the Tree.** The Peek holds the page's own Status, Assignee, Priority and Labels pickers (`PropertyPickers.tsx`), so a letter on the Tree opens the Peek for that issue if it is closed and opens the picker inside it. A popover anchored to the row would need a second copy of each picker and its queries, and the Peek keeps the list in view. The shortcut clicks the control that carries `aria-keyshortcuts` with that key, in the page when one is open and in the Peek otherwise, so keyboard and mouse open the same picker. The click does not move focus, so when the picker closes the browser hands focus back to where the key was pressed: `S`, an arrow, Enter and `J` run without the mouse. The pickers show their key in a tooltip ("Status (S)"), the summary button shows "Edit summary (E)", and the Issues header has a Search button for `Cmd+K`.
- **Palette.** A modal `<dialog>` with a combobox (`aria-activedescendant`) over a listbox, searching the loaded issues by key and summary as you type (Q37 option a; descriptions, comments and raw JQL are not searched, so there is no IPC channel and nothing to debounce or abort). Done issues count once they have loaded. Every word must appear in the key or summary; an exact key ranks first, then a key prefix or a bare number that ends the key, then a summary prefix, then the rest, open before Done and newest first. It lists 50 and says how many more match. Arrow keys move, Enter opens the issue's full page (and makes its row active when the Tree shows it), a click does the same, `Esc` closes and focus returns to where it was. Enter opens the page only: a Peek needs the issue in the Tree, which a filter may hide.
- **Esc.** The innermost control that has focus wins, because each handler skips an event another already handled and a field, picker or dialog keeps its own `Esc`. In order: the palette or another dialog closes; an open picker closes; the summary field cancels its edit; the Tree or the page handles it (the Tree closes the Peek, the page returns to the Tree; the page covers the Peek, so it leaves first and a second `Esc` closes the Peek); and when focus is elsewhere (a button in the Peek, the sidebar, the body) the global listener does the same two steps, the page first and then the Peek. The text filter keeps D2's rule: `Esc` clears it, then returns focus to the Tree.
- **Undo.** Every field edit Jira accepts goes on an in-memory stack of the last 50 (status, assignee, labels, priority, dates, estimates, sprint, parent, Customer, Engagement, type, summary), and its toast says what changed with an Undo button. `Cmd+Z` or the button takes the newest edit off the stack and writes the old value back through the same mutation as the edit, so the Tree and the Peek show it at once and a refusal rolls it back. The stack ends with the session and is cleared on logout. Redo is not offered, and an undo is not itself recorded, so `Cmd+Z` again walks further back. Creates, deletes, comments, worklogs, attachments and links never reach the stack (Q38).
  - An undo is refused, and its entry dropped, when the issue no longer shows what the edit set, because Jira or someone else changed it since: the toast says which field and nothing is sent. The check compares people, options and sprints by id and labels as a set, against the caches the focus refetch keeps fresh, so a change Jira made to the same field itself (automation) also refuses.
  - An edit core cannot reverse is a barrier: setting a Priority, Customer, Engagement, parent or original estimate from nothing has no "clear" in `issues:edit`. Its toast has no Undo button, and `Cmd+Z` drops it with a warning, so the stack never silently skips to an older edit.
  - A write Jira refuses on undo rolls back and warns, and its entry is dropped, so the next `Cmd+Z` reaches the edit before it instead of repeating a refusal.
  - Nothing to undo says so in a toast. Text typed in a field keeps its native undo; the app's undo never runs there.

## Create and Delete

- `C` opens the create modal (see Keyboard for the rules every letter shares). It is off until the Tree has loaded. The New issue button in the Issues header does the same, so the shortcut has a visible alternative.
- The form starts as a Story (Q33). With an issue selected (the active row, a "N done" chip's open parent, or the page's issue) the parent is the nearest Epic at or above it, the Epic itself when an Epic is selected. Customer and Engagement come from that Epic, else from the selected issue: the Epic wins, so a new Story does not start as the Customer mismatch Q15 flags. A Customer header supplies its Customer alone. Sprint, assignee, priority, labels and estimate start empty. Changing the type keeps a parent that still fits and otherwise takes the type's own default: a Subtask goes under the selected Story, an Epic has no parent.
- Summary, Customer and Engagement are required on every type, Task and Bug included (Q14), and a Subtask needs a parent. The Create button stays disabled and a line under the form says what is missing. An Epic has no parent, sprint or estimate; a Subtask has no sprint (`propertyRules`). The pickers are the page's own `Picker`, fed by the same hooks, and choosing a parent whose Customer or Engagement differs opens the Q16 prompt, which here says "Move this issue under". With no Customer or Engagement chosen yet, the parent's values start the form without a question.
- Create sends `issues:create`. Core's `createIssue` makes the issue and reads it back; main then moves it into the chosen sprint, since core's create takes none, and reads it again. The form stays locked, and Esc does nothing, until Jira answers. The read-back goes into the cache of its phase and the Tree selects it, opening any collapsed Epic or Customer above it first; no list is reloaded. A filter that hides the new issue leaves the selection where it was.
- PSAPAC's automation rewrites new issues, so the notice after a create compares the form with what Jira holds: it names the key and summary, then each of Customer, Engagement, Parent, Sprint and Original estimate that differs ("Customer is Collibra (Internal team) (you chose Acme)") and any label Jira added. A failed step after the create (the sprint move or a read-back) is a warning on the notice, which stays until dismissed; the issue exists either way. When the read-back failed the unresolved list reloads to show it.
- "Create more" keeps the modal open with everything but the summary, shows the notice inside the modal (the Tree behind it is inert) and focuses the summary. Cmd+Enter creates from anywhere in the form.
- The delete confirmation opens from the Delete button on the Peek and on the page; there is no key for it. It reads the issue afresh (`issues:get`) and lists every subtask Jira deletes with it, which the confirm button names ("Delete issue and 2 subtasks"). Confirming a list of subtasks is the choice to cascade; with none, the delete sends no cascade. Cancel has focus, so Enter never deletes, and Esc or Cancel returns focus to the Delete button. Child issues that are not subtasks, such as an Epic's Stories, are not deleted: the dialog says they lose their parent and names the first five.
- Delete is optimistic. The dialog closes at once, the issue and the subtasks chosen leave both lists, the children that stay lose their parent, and the page or Peek that showed it closes. A refusal puts everything back and the notice says so; a success says what went. No issue is read afterwards, so the next focus refetch of the unresolved list reconciles; a phase still on its first load starts again when the deleted issue was in no loaded list, since that load may have paged past it. The dialog holds the issue it was opened for, so it neither depends on the lists holding it (a Done parent opened from a child's page before Done loads) nor closes if a refetch drops it. `issues:delete` reads the subtasks again and refuses to delete an issue that has subtasks without the cascade, and refuses a cascade to a subtask the user was not shown, so one added since the dialog opened is never deleted unseen.
- The modals are native `<dialog>` elements through `Modal`: the page goes inert, Tab stays inside, Esc closes, and focus returns to the control that opened it, or to the Tree when that control has gone.

## Saved Views

- The sidebar's Views section lists `views.json`, the file `jm view list` and `jm issue list --view` read. Core's `createView`, `renameView` and `deleteView` do the work in main, so a view made here shows in the CLI and the reverse. Before the file exists the list shows the starters, "My issues" and "Current sprint"; they are ordinary views once the first change writes the file, so they can be renamed and deleted.
- Clicking a view replaces the filter bar's filters with the view's and sets the three toggles to the view's. The toggles go through the same write as a press on a toggle button, so they are written to `settings.json` and stay as the view left them after a restart (Q28: each toggle remembers its last state). The filters last for the session, as before.
- The view that equals the filter bar and the toggles is marked (`aria-current`). It is derived on each render, so it stops being active the moment a filter or toggle changes, and a bar built by hand that matches a view marks it.
- New view (the + beside the heading) saves the current filters and toggles under a name typed inline. Enter saves, Esc cancels, and a taken or empty name keeps the field open with core's message. Core makes the id, a slug of the name, so the row appears when the write answers.
- Rename is an inline field (pencil button, or F2 on a focused view): Enter or leaving the field saves, Esc cancels, and the id stays. Rename and delete are optimistic: the list changes at once and a refusal puts the old name or the view back and shows the error under the list. Delete asks inline, in place of the row, with Cancel focused; Esc cancels. Focus goes back to a view button afterwards.
- Up and Down move between the views. There are no single-letter shortcuts.
- Main runs every views call through one promise chain, since core reads, changes and rewrites the whole file and two overlapping calls would drop an edit. There is no lock file: the CLI only reads `views.json`. A CLI command that writes views must lock the file first, as core's timer does for `timer.json`.
- A view is read again on window focus, so a hand edit of the file shows up when the window regains focus.

## IPC

- Add a channel in three places: the `IpcContract` entry and the `CHANNELS` list in `src/shared/ipc.ts`, a zod schema in `argSchemas` and a handler in `createHandlers` in `src/main/handlers.ts`. The compiler fails when one is missing.
- Every handler returns `{ ok: true, data }` or `{ ok: false, error: { code, message } }`, the core error shape. A thrown `Error` loses its fields crossing IPC, so nothing throws across it. An error that is not a `JiraMgrError` becomes `internal` with a fixed message.
- Main answers only the main frame of one of its own windows while that frame shows the app's page (`src/main/trust.ts`). It refuses every permission request from the page, such as notifications and camera.
- Main validates every argument at the boundary. The schemas check shape and length; core owns the deeper rules and answers `validation_failed`.
- The token goes renderer to main once, at login, and stays in main. No channel returns it, and no error message or log line carries it, with `JM_DEBUG=1` too, which logs stack frames and never the message. The login mutation has `gcTime: 0`, so the cache drops the token with the login screen. Until then it sits in the renderer's memory, as the typed value does.
- Each handler gets a second argument, `{ sendProgress }`, built from the requesting window's sender. `issues:list` reports each page through it as the `issues:progress` event, which preload exposes as `onIssuesProgress`. The renderer numbers every load and ignores progress for any other load id.
- `issues:list` loads one phase. A new load of a phase aborts the one running for it, and `session:logout` aborts both before the token is removed. An aborted load answers `null`, never an error.
- Page channels: `issues:get` reads one issue with its description and subtasks; `issues:edit` sends a strict `changes` object (assignee, priority, dates, labels to add or remove, parent, Customer, Engagement, original estimate, Time remaining, type); `issues:setStatus` and `issues:setSprint` move by target status and by sprint; `issues:transitions`, `sprints:list`, `users:search` and `fields:options` feed the pickers. Every write refuses an issue outside the settings project through `assertInProject`, a new parent included, and a type change reads the issue first and refuses an Epic or Subtask, as `jm issue edit` does.
- `issues:create` takes a strict object (type, summary, Customer and Engagement ids, and optionally parent, assignee, priority, labels, estimate and sprint) and answers `{ key, issue, warning }`. `issues:delete` takes the key, whether to cascade and the subtasks the user was shown, and answers the keys deleted. Both refuse an issue or parent outside the settings project through `assertInProject`.
- Main rewrites the CLI wording in a core error message before it crosses IPC (`src/main/messages.ts`), so "Run `jm auth login`" reads "Log in again." in the app. The error code and every other word stay as core wrote them, and the CLI never passes through it.
- `settings:setToggles` writes through a promise chain, so two quick presses write in order. It replaces only `toggles` and keeps the rest of the settings.
- `views:list`, `views:create`, `views:rename` and `views:delete` take strict objects: a name of at most 80 characters, filters in core's shape (lists of strings, a text string) and the three toggles. Core owns the name rules (trimmed, not empty, unique in any case) and answers `validation_failed` or `not_found`.
- Window focus travels the other way: main sends `window:focus`, and the renderer hands it to TanStack Query's focus manager. Chromium raises `visibilitychange` only when a window hides, so the default would miss a switch back from another app.

## Rules

- Context isolation and the sandbox stay on, and Node integration stays off. The renderer reaches the main process only through `contextBridge` in the preload script.
- The renderer imports only the renderer-safe core entry points: `@jira-mgr/core`, `/issue`, `/hierarchy`, `/adf`, `/timer-calc` and `/view-filter`. Node-only entry points (`/auth`, `/http`, `/search`, `/write`, `/state` and the rest) belong to the main process. `src/shared/ipc.ts` imports the `SavedView` type from `/state` with `import type`, which leaves nothing of it in the renderer bundle.
- The main process calls `@jira-mgr/core` and nothing else. Business rules live there. The write guard that refuses an issue outside the settings project is core's `assertInProject`, shared with the CLI.
- electron-vite bundles `@jira-mgr/core`, `zod` and the other `devDependencies`. Dependencies stay external in the main process.
- The package emits CommonJS, not ES modules, so the preload script can run in the sandbox. `electron.vite.config.ts` lists the main entries under `lib`, because `rollupOptions.input` drops the CommonJS and `electron` external settings with Vite 8.
- The e2e entry (`out/main/e2e.js`) is test code built beside the real one. `scripts/package.ts` leaves it out of the app, and fails the package if `e2e.js`, a fake Jira marker or a `require` of anything but `electron` and `node:` built-ins reaches it. Keep every runtime import bundled: the packaged app has no `node_modules`.
- The package is Electron's prebuilt `Electron.app` with `out/` as its app, renamed and signed ad hoc, so it needs no packaging dependency. No code signing identity and no auto-update: the app builds and runs locally.

## Known Limits

- The Tree shows nothing until a whole phase has loaded, since a partial phase can hold a Story whose Epic is on a later page.
- The renderer cannot cancel a load by itself. A newer load of a phase and logout abort the one running; an unmounted query otherwise runs to the end.
- Filter choices other than statuses come from the loaded issues, so an issue that is not loaded cannot be filtered for.
- Saved views have no order controls and no "update this view with the current filters": delete it and save it again.
- Row heights are fixed. A row with a second line would need a rewrite of the window.
- The theme choice lives in `localStorage`, not in the settings file, which the CLI also reads. Move it there if the CLI should honour it.
- Opening the Peek narrows the Tree, which can wrap the toolbar onto another line and move the rows by one, so a double click on a row lands on its neighbour. Enter and the Peek's Open button open the page.
- The page cannot clear a parent, since core's `editIssue` takes a key only, and cannot clear the original estimate, since it takes a duration only.
- "Recent assignees" are the people on the most recently updated loaded issues, since Jira keeps no record of who the user assigned to.
- The label list is the labels on the issues loaded so far, so a label used only by a Done issue appears once Done has loaded.
- The optimistic estimate assumes 8 hours to a day and 5 days to a week. A site with other working time shows the difference until Jira answers.
- The create modal has no description (D4's editor), start or due date, and no estimate of its own beyond the original estimate. A create that PSAPAC's automation rewrites shows the difference in the notice and does not undo it.
- Done children that are not subtasks, of a deleted unresolved Epic, can still show its parent key if the Done phase was still loading when the delete ran, since the delete edits only the lists it holds and the Epic was in a loaded one, so the Done load does not restart. They keep it until Done goes stale (five minutes).
- A subtask added between main's re-read of the subtasks and the delete request still goes with the cascade, since Jira has no conditional delete. The window is one request.
- What Jira does with the children of a deleted Epic (they stay, without a parent) is Jira's documented behaviour and is simulated by the e2e fake. No live PSAPAC delete has checked it.
- The description is read-only text until D4's editor, and the page lists no comments, worklogs, attachments or links yet.
- Subtasks list only on the page, where `getIssue` returns them; the Tree builds Subtasks from the parent keys of the loaded issues.
