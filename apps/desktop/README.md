# Desktop App

The Electron app, package `@jira-mgr/desktop`, built with electron-vite. The renderer lives here too: React, Tailwind and TanStack Query. Today it logs in, then shows a sidebar with the saved views and the Tree: the project's issues grouped by Customer, Epic and child, with a toolbar of toggles and filters, `J` and `K` navigation, and a space-bar Peek. The summary edits in place on the Peek and on the issue page. Enter, or a double-click on an issue row, opens an issue's full page, with a properties sidebar of pickers and a TipTap description editor. `C` opens a create modal, and a Delete button on the Peek and the page opens a confirmation that lists the subtasks it deletes. `Cmd+K` opens the palette: the issue's actions, saved views, the loaded issues and Jira text search. `S`, `A`, `L`, `P` and `E` open the active issue's pickers and summary editor, `Shift+S`, `Shift+D`, `Shift+P`, `Shift+E` and `Shift+C` its start date, due date, parent, original estimate and sprint, `I` assigns it to you, a right-click on an issue row (or `Shift+F10`) opens a menu of 18 issue actions, `Y` and `U` copy its key and its Jira link, a click on a row's status dot, priority slot, avatar or Labels, Sprint, Due date or Start date slot opens that property's editor beside it, the Original estimate slot edits in place, `E` on the Tree edits the summary in a modal, a "+" on a group header creates an issue in that Customer, `1` to `9` choose in the Status and Priority pickers, and `Cmd+Z` undoes the last field edit. `X`, `Shift+Up`, `Shift+Down`, `Shift+click` and `Cmd+A` check issues in the Tree, and a bar over its foot sets one property on all of them in one batch (Status first, then an Actions menu), which `Cmd+Z` undoes as one. The page also lists and edits the issue's links, worklogs, comments and attachments, and a file dropped anywhere on it attaches. `W`, the menu's Log work, the palette's Log work and a click on a row's Logged slot (on the Tree and the Sprint page, empty or filled, never on an Epic) open a Log work modal that holds the worklog form: Time spent, Started and Comment, saved with Enter, closed by Esc or Cancel with no write, kept open with the text and the error when Jira refuses; on save the row's Logged, Remaining and Remaining % follow the re-read. `T` starts the timer on the active issue and stops it again through a dialog that logs the time as a worklog; the elapsed time shows on the row, the issue page and the sidebar, and a reminder notification fires while a timer runs past the threshold, even with every window closed. The timer is `jm timer`'s own `timer.json`, so either side can stop what the other started. The reminder memory lives in the app's process, so a restarted app reminds again at once. Light or dark theme.

## Run

```
pnpm dev     # app with hot reload
pnpm build   # writes apps/desktop/out
pnpm test    # Vitest: IPC validation, backend loads and views, tree model, optimistic updates, queries
```

`pnpm package` (from the repository root) builds the app and assembles the unsigned `dist/jira-mgr.app`. [Install the Desktop App](../../docs/how-to/install-desktop-app.md) covers installing it.

`pnpm dev` and a normal launch read and write the real state folder and Keychain item. Set `JM_STATE_DIR` to a scratch folder for any manual run that must not touch them.

## Layout

```
src/shared/     the IPC contract: channel names and payload types, shared by all three sides
src/main/       main process: window, IPC handlers, the backend that calls core
src/preload/    preload script: the only bridge to the renderer
src/renderer/   React renderer
build/          the app icon: icon.svg is the source, icon.png and icon.icns are built from it
```

## Tree

- Loading: `['issues', 'unresolved']`, `['toggles']` and `['me']` start together. The Tree renders once the unresolved phase, the toggles and the display have data (`['toggles']` and `['display']` read the same file), and `me` when "Assignee: me" or the assignee filter needs it. `['issues', 'done']` then loads in the background, always, since progress counts need the Done issues and, with "Hide done" off, the Tree shows them. The toolbar shows the running count. An edit reads only the edited issue again and leaves both phase loads alone.
- The Tree has no grouping, sorting or Done rules of its own: `buildHierarchy` and `issueMatcher` from core decide, as `jm issue tree` does. With "Hide done" on, the Tree shows no Done issue: no Done row, no Done context ancestor and no "N done" chip, whether or not the Done phase has loaded. An open Story whose Epic is Done sits under No Epic, as in `jm issue tree`, and a match whose only ancestors are Done adds no Customer group.
- Rows are 32 pixels tall and only the rows in view, plus 10 of overscan and the active row, are in the DOM. Scroll anchoring keeps the first visible row where it is when a rebuild changes the rows above it.
- A Story whose Customer differs from its Epic's carries a "Customer differs" chip; the `title` and the Peek name both values.
- An issue row ends its title with a blocked pill (a disc and the count of open issues holding it up) and a blocking pill (a square and the count of open issues it holds up; the tooltip reads "Blocking 2 issues"), each only when its count is above 0 (#144). Only "Blocks" links count, and an end counts until it is Done (`openBlocks` in core's `view-filter`, which prefers a loaded issue's status). The row's accessible name includes the same words, before priority and due, and the Peek lists the blockers under Blocked by. A link added or removed from the page refreshes both ends, when the write succeeds and the end is loaded.
- The Filter menu lists 15 fields, in Linear's order and then this project's own: Status, Status type, Assignee, Creator, Priority, Type, Label, Relations, the dates Due date, Created and Updated, then Customer, Engagement, Epic and Sprint. Each opens a checkbox list. Every field but the dates has an "is" and "is not" switch above its list: "is" keeps the issues that hold a checked value, "is not" leaves them out, and a field can hold both. A date field takes one window (Overdue, Today, Next 7 days, Last 7 days, Last 30 days), so checking another replaces it. Each field and operator with values draws its own chip ("Status: Done", "Status is not: Hold") with a remove button. The Customer list is the Project's Customers, fetched when the menu first opens, so a Customer with no issue is still offered; the Epic list is the loaded Epics. `F` opens the menu. The filters live in `ViewFilters` (`filters.ts` reads and writes them with `valuesOf` and `toggleChoice`), and `issueMatcher` in core applies them.
- With no rows, the Tree area names the cause: `No issues match "text" with Type: Bug`, the toggles that are on on a muted line ("Hide empty Customers is also on."), and one primary Clear filters button. The chip row's own Clear steps aside while the empty state shows, so one button clears. `noMatchTitle` in `filters.ts` builds the title. A failed Done load shows the banner "Could not load Done issues. Done counts are hidden." above the Tree, with Retry.
- Rows sit inset 8 pixels from the Tree's edges with an 8 pixel radius. Three row fills show state, and none draws a ring, edge or side bar: the active row while the Tree has focus (`--row-focus`), the row the Peek shows (`--row-selected`, with weight 500, `aria-selected` and a bold key), and a row that is both (`--row-selected-focus`). The Tree container draws no outline. The fills stay light in the light theme and dark in the dark one so the grey and coloured glyphs keep 3:1 on every one (`contrast.test.ts`), which leaves little room between them: focus against selected is 1.03:1 in light and 1.12:1 in dark, so the weight and the bold key carry the difference too. ## Column Headers

Added in #275. A header row (`ColumnHeader.tsx`, `role="group"` named "Column widths") sits above the Tree's list at `@tree` width and up, naming each Display property in grey with the Display menu's label (`PROPERTY_LABELS`), right-aligned over the right-aligned values. The key, status, priority and avatar keep their anatomy and get no header. It is hidden with the strip below 700px of Tree width, and it is never faded.

- **Widths.** A column starts at its default (`SLOT_WIDTH` in `propertyFit.ts`: Labels 96, Sprint 104, the three time slots 64, Remaining % 48, Start date 96, Due date 96, Created and Updated 72) and takes the user's width from `display.widths` once one is saved. `IssueTree` sets each width as a CSS custom property (`--col-labels`, `--col-estimate` and so on) on its container, and every cell reads it through `colWidth(property)` with the default as the fallback, so a drag repaints the rows with no React render per row and the memoised `TreeRow` is untouched. A new Display property needs a `SLOT_WIDTH` entry and `style={colWidth(...)}` on its cell, and nothing else: the header, the fit and the drag read `ROW_PROPERTIES` generically.
- **Room.** `fittingCount` is gone: no column drops because the window is narrow. `stripRoom` gives the pixels the strip may take with the title at `5rem` in the deepest row with the widest extras; when the saved widths and the gaps exceed it, `fitWidths` takes the excess from the trailing column first (to 0), then the one before it. That is only what is drawn: the saved widths are kept, and widening the window restores them. A drag is capped (`dragCap`) at what the other columns leave, so the title keeps its minimum; the pointer keeps moving and the column stops.
- **Alignment.** The strip hangs from the avatar, so the header ends 44px (row inset 8, row padding 8, avatar 20, gap 8) plus the list's scrollbar (`offsetWidth - clientWidth`, read by the Tree's `ResizeObserver`) from the right edge, and each header cell has its column's width, so header and rows line up with macOS overlay scrollbars and with Linux's 15px ones.
- **Separators.** Each column has a separator on its left edge (the first sits after the title): the strip hangs from the right, so a column grows leftwards and the pointer stays on the edge it drags. Each is a focusable `role="separator"` with `aria-orientation="vertical"`, `aria-valuenow` (the drawn width), `aria-valuemin="0"`, `aria-valuemax` (the cap) and the name "Resize Original estimate column".
- **Mouse.** A drag uses pointer events with capture on the separator and `preventDefault` on the press, so it starts no row drag, selects no text, makes no row active and opens no Peek (the header sits outside the rows). Moving left widens the column, rounded to whole pixels between 0 and the cap. At 0 the column is empty, its separator turns red and a status line reads `Release to remove <name>`. Releasing saves the width and removes the column at 0; Escape (captured, so the page's own Escape does not fire) puts the column back and ends the drag. Focus returns to the Tree after any drag.
- **Keyboard.** On a focused separator, Left widens and Right narrows by 8px, 32px with Shift, each press saved at once. Right stops at 1px, so a held key cannot remove a column. Delete or Backspace removes the column and puts focus on the Tree, including a column the window draws at 0 (its separator has `tabindex="-1"`, so it is no tab stop).
- **Saving.** Release and keys go through `resizeColumn` in `Shell`, which writes the display as the Display menu does (`useSetDisplay`): at once in the cache, then to `settings.json`, with the same refetch on a refusal. A width above 0 is saved in `display.widths`. Removing a column, by release at 0, by Delete or by turning its chip off, drops the property from `display.properties` and its entry from `display.widths` (`withoutProperty`), so adding it again starts at the default. Because the view stays lit while the display changes, Update view wakes (`viewDisplayMatches` compares widths against the defaults) and saves the widths into the view.
- **Cut columns.** A cell narrower than 16px (`MIN_CELL`, a column fitted to 0 or saved at 1px) is no anchor for an editor: `Shift+E` and the other cell keys check `cellUsable` and fall back to the Peek's picker or the menu, as for a hidden slot. A drag is capped at `WIDTH_MAX` (1000px) as well as by the room, so it never builds a width the saved file refuses. Header names carry a `title` with the full label.
- **Sprint page.** One header row above the first status section, drawn only, at the widths set in the Tree, each floored at 16px because its cells are buttons. The Sprint page's cells are `Slot` buttons with their own editors and are not changed.

## Description Editor

- The Description section is one TipTap instance that shows the description and edits it, so the read view looks as editing will. **Edit description** (or **Add description** when empty), or a click on plain text, starts an edit. Markdown shortcuts work as typed: `#` to `######`, `-`, `1.`, `>`, three backticks, `---`, `**bold**`, `*italic*`, `~~strike~~` and `` `code` ``. There is no link dialog: type or paste a URL.
- `Cmd+Enter` or **Save** writes; `Esc` or **Cancel** leaves, through the discard dialog when the text changed. There is no autosave, since each write is a history entry. Save is off while nothing changed and while an image is uploading or failed.
- Panels, tables, macros, expands, task lists, mentions, dates, cards and anything else the editor has no node for stay as the original ADF in a read-only block or chip. They can be selected, moved and deleted, never edited, and save unchanged. A block the converter or the schema would alter loads read-only whole.
- The converter lives in core (`adfToEditor`, `editorToAdf`). `editor/extensions.ts` gives each node and mark the name the converter emits, and `schema.test.ts` runs every recorded fixture through the real schema.
- Save checks Jira first. `issues:setDescription` carries the edited document and the one the edit began on, reads the issue, and writes only when Jira's description still equals that base (by value, so the user's own field edits raise nothing). Otherwise it writes nothing and returns Jira's, and the page offers **Save mine anyway** (against Jira's current) or **Discard mine**. Jira has no conditional write, so an edit that lands between the read and the write still loses.
- A save shows at once and rolls back if Jira refuses. The editor stays mounted through it, so a refusal or a conflict reopens it with the draft, the caret and the undo history as left. **Edit description** reads "Saving" and stays off until the re-read after the save lands, so the next edit starts from Jira's stored form.
- Unsaved text is a draft for the session (`drafts.ts`): opening another issue, Back, or the Tree keeps it, and coming back reopens the editor with "Unsaved draft restored." While any draft exists the renderer sets `onbeforeunload`, and main answers Electron's `will-prevent-unload` with a native Quit or Stay dialog. Logout asks first and names how many drafts it drops (descriptions and comments); it then clears the drafts, the uploads and the image cache.
- An image dropped or pasted (PNG, JPEG, GIF or WebP, at most 100 MB) uploads on drop (`attachments:addImage`), shows a placeholder, and embeds as a `mediaSingle` with the media id Jira gives the attachment. Main checks the magic bytes against the claimed type, refuses unsafe names and rewrites the extension. Cancelling the edit leaves the attachment on the issue. A saved image loads through `attachments:image`: main finds the attachment whose content redirect names the media id (4 at a time, cached per issue, a miss cached for 30 seconds), reads at most 20 MB, checks the bytes, and the renderer shows them from an object URL. The token and the media URL never reach the renderer.
- Links open in the browser: a plain click when reading, `Cmd`+click when editing. The renderer and main both pass the URL through `externalUrl` (`http:`, `https:`, `mailto:` only), and the editor never lets a click follow a link in the window. HTML pasted from another app has its `data-adf*` attributes stripped, so it cannot plant a mention or a block; only a copy made in this editor in this session may carry raw ADF back.
- The issue page has a 24/600/32 title over 14/22 body text, in a column capped at 40rem (`max-w-[40rem]`) with 32px between blocks. Section headings (Description, Subtasks, Links, Time tracking, Worklogs, Activity, Attachments) are 13/600 ink in sentence case, and a 1px `--line` rule sits above Links, Time tracking, Worklogs, Activity and Attachments. The Properties groups keep their small uppercase headings. The Description starts by y=140 at the top of the page.
- Dragging a file over the issue page lights up its drop zones (`fileDrag.ts` tracks the drag for the whole page; `DropZone` is one zone, declared with a label and a handler, so several can show at once). The description's zone reads "Add images into description": dropping an image there, without clicking Edit, opens the editor and embeds it at the end through the same upload path as a drop in the editor; any other file attaches to the issue instead (see Activity). Each zone shows a 20px upload icon over its label on a `bg-canvas/95` surface with an inset 2px dashed accent border, and the zone's own content fades to 20% opacity, so no legible text lies under the label (`e2e/desktop/surfaces.test.ts`). The highlight clears when the drag leaves the window, on a drop and on Esc. The window never navigates to a dropped file. An issue deleted since, found when the page reads it again, sends the page back to the Tree with a notice.
- A saved description is on the undo stack. `Cmd+Z` outside the editor writes the previous description back, unless Jira's description changed since (key order and `localId`s are ignored in that check).
- Keyboard: the editor binds no single letter and leaves `Cmd+K` to the Palette. `Tab` and `Shift+Tab` indent in a list and otherwise move to Save and Cancel. `Cmd+Z` is the editor's own history.

- **Target.** `S`, `A`, `L`, `P`, `E`, `W`, `I`, `Y` and `U` act on the open page's issue, else on the active Tree row's issue, and on none while the Inbox, a Sprint page, the Epics table or the Customers page hides the Tree. The Shell reads that one target (`targetKey`) for these keys, the timer and the palette's context, and `openCreate` starts from no selection there, so none can act on a row the user cannot see. A Customer header, a "N done" chip or no active row has no issue, so the key does nothing. Ctrl stands in for Cmd off the Mac.
- **Guard.** A letter is a command only alone: not with Cmd, Ctrl or Alt, not held down, not during IME composition, not already handled, never when focus is in a text field, picker, dialog, popover, `contenteditable` or an element with the `textbox`, `combobox`, `listbox` or `menu` role (`keepsLetters`), and only when focus is inside the Tree, the Peek or the issue page, each marked `data-key-scope`. `T` or `C` on a sidebar or toolbar button does nothing. `/` and `?` obey the same rules except the last, so they reach the filter and the shortcut list from a button too; it does nothing under an open page, whose list is inert. `Cmd+Z` and `Esc` obey the same target rule, so a text field keeps its native undo and a picker keeps its own `Esc`. `Cmd+K` opens from a text field, since it edits nothing there, but not over a dialog or an open picker.
- **Filter to Tree.** `Enter` or `ArrowDown` in the text filter makes the first issue row active, skipping Customer and group headers (the first row when no issue row shows), and moves focus to the Tree. The query stays, so `J` and `K` walk the matches. `Esc` in the filter still clears it, then returns to the Tree.
- **Skip link.** A visually hidden "Skip to issues" link is the first Tab stop in the Shell. It shows at the top of the sidebar on focus, with no coloured border, and `Enter` moves focus to the Tree (or to the page when one is open). With no rows, a ring in the global focus outline is painted over the "No issues match" panel while the Tree has focus, so an empty Tree still shows where focus is.
- **Pickers from the Tree.** The Peek holds the page's own Status, Assignee, Priority and Labels pickers (`PropertyPickers.tsx`), so a letter on the Tree opens the Peek for that issue if it is closed and opens the picker inside it. `S`, `A`, `P` and `L` on the Tree are the exceptions: they open the cell editor on the active row's status dot, avatar, priority slot and labels slot (see Cell Editor), and `L` falls back to the Peek when the slot is not drawn. The other letters click the control that carries `aria-keyshortcuts` with that key, in the page when one is open and in the Peek otherwise, so keyboard and mouse open the same picker. The click does not move focus, so when the picker closes the browser hands focus back to where the key was pressed: `S`, an arrow, Enter and `J` run without the mouse. A click on a row's status dot, avatar, priority slot, labels slot, Sprint slot, Due date slot or Start date slot makes the row active and opens the cell editor, so the pointer and the keyboard land in one place. The four pickers show their key as a keycap at the right of the row on hover and focus, the Status and Priority options show a keycap of their own number and answer to `1` to `9` (`numbered` on `Picker`; the searchable pickers type digits, so they have none), the summary shows "Edit summary (E)" on hover, and the Issues header has Shortcuts, Search and New issue buttons that carry their keycaps (`?`, ⌘K, `C`).
- **Palette.** Its context is that same target, so under the Inbox, a Sprint page, the Epics table or the Customers page it lists no actions for the hidden Tree row. A modal `<dialog>` with a combobox (`aria-activedescendant`) over a listbox of 36px rows (the footer draws Enter and Esc as keycaps), searching the loaded issues by key and summary as you type (Q37 option a). Below them a "Search text in Jira" group lists issues whose description, comments or other text hold the query (Q37 chose option a, loaded issues only; this adds the text search that option b described, and raw JQL, option c, is still not offered). The group appears from three characters, runs `issues:searchText` once the field has held still for 300 ms, shows "Searching" until the answer lands and "N more matches" or "No more matches" after it, and shows "Failed: <message>" when Jira errors. Its rows are options like the others, never repeat a loaded match, keep Jira's order (most recently updated first, 50 at most) and sit below every loaded match, so the loaded ranking stays first and the arrow keys walk both lists. A loaded issue whose key and summary miss the query but whose description holds it appears in the group. Jira matches whole words, so the group finds `runbook` and not `runb`. Done issues count once they have loaded. Every word must appear in the key or summary; an exact key ranks first, then a key prefix or a bare number that ends the key, then a summary prefix, then the rest, open before Done and newest first. It lists 50 and says how many more match. Arrow keys move, Enter or a click runs a row (an issue opens its full page, and its row becomes active when the Tree shows it), `Esc` closes and focus returns to where it was. An issue row opens the page only: a Peek needs the issue in the Tree, which a filter may hide. **Issue actions (#141).** The issue in context is the page's issue, else the Tree's active row when no Inbox or Sprint page covers it (the one the letter keys act on); it shows as a chip (type icon, key and summary) left of the field, and the field's `aria-describedby` points at it. With a context issue, an Actions group lists, first and in this order: Assign (`A`), Assign to me (`I`), Change status (`S`), Change priority (`P`), Add labels (`L`), Set sprint, Create sub-issue, Copy key (`Y`), Copy link (`U`) and Open in Jira. The key shows as a keycap (`Kbd`) beside an action only when a global shortcut runs it, read from `keymap.ts` (`keyOf`), so Set sprint, Create sub-issue and Open in Jira show none. An action is listed only when the issue's type allows it: an Epic or a Subtask has neither Set sprint nor Create sub-issue. Each action runs the code its key or picker runs: the pickers are the Peek's (opened from the Tree) or the page's, found as `S`, `A`, `L` and `P` find them; Assign to me is `assignToMe`; Copy key and Copy link are `copyIssue`; Open in Jira opens `/browse/<key>` through the same window-open check as every link. Set sprint opens the issue's page on its Sprint picker, because the Peek has no Sprint picker. Create sub-issue opens the create modal as a Subtask under the issue. A "Views" group lists each saved view as "Go to view <name>", which applies it as a click in the sidebar does; it shows with no issue in context too. What you type narrows the actions by label and the views by name (every word must appear); both stay above the issues. Enter opens the highlighted row, and the highlight starts on the first loaded issue whenever one matches, with or without a query, so Enter opens an issue as it did before the palette had actions, even when a typed word is also in an action's label. The arrow keys reach the actions and views above it, and Enter on one runs it. The highlight starts on the first action or view only when no loaded issue matches, and on the first Jira text match only when nothing else is listed, so Jira's results landing after a pause never move it. The list opens scrolled to its top, so the actions show; only an arrow key scrolls to the highlight. The views and the actions follow the field at once, but the issue list lags it a render, so an Enter in that gap opens the current query's top issue unless an arrow key already chose an action or view. The palette closes before an action runs, so a picker or the create modal takes focus cleanly. Actions apply to the one issue in context; the palette does not act on checked issues, which the bulk bar (#143) handles.
- **Issue menu.** `IssueMenu` opens on a right-click, the context-menu key or `Shift+F10` over an issue row of the Tree, the Sprint page, the Epics page or the Inbox (each row carries `data-issue-key`, or is a `treeitem`), at the pointer and moved to stay in the window. It lists 18 actions (`menuItems.ts`): View full screen, Status, Assignee, Start date, Due date, Sprint, Rename, Parent, Type, Labels, Priority, Original estimate, Log work, Related issues, Copy, Open in Jira, Add comment and Delete, minus what the type lacks. It acts on the row clicked, whatever is checked, and leaves the selection and the Peek alone. Its submenus are the pickers' own lists (`Picker`'s `menu` variant), so each edit is the page's optimistic edit; Start date, Due date, Original estimate and Rename open a popover with the page's `TextField`. View full screen opens the issue page; Add comment and Related issues open it and then focus the comment box or press Add link; Log work opens the Log work modal; Copy opens the create dialog seeded from the issue (its images and its comments, worklogs, links, sprint and dates stay behind, and the assignee is the create default); Delete opens the usual confirmation. It is a manual popover, closed by a press outside, `Esc` or a finished action, and focus returns to the row. `Up`, `Down`, `Home` and `End` move, `Right` or `Enter` opens a submenu, `Left` closes a list of options (the date, estimate and Rename fields keep it for the caret, and only `Esc` closes them), `Tab` closes the menu, and a listed key runs its item (a held key does not repeat it).
- **Esc.** The innermost control that has focus wins, because each handler skips an event another already handled and a field, picker or dialog keeps its own `Esc`. In order: the palette or another dialog closes; an open picker closes; the summary field cancels its edit; the Tree or the page handles it (the Tree clears the checked issues first and then closes the Peek, the page returns to the Tree; the page covers the Peek, so it leaves first and a second `Esc` closes the Peek); and when focus is elsewhere (a button in the Peek, the sidebar, the body) the global listener does the same steps, the page first, then the checked issues and then the Peek. The text filter keeps D2's rule: `Esc` clears it, then returns focus to the Tree.
- **Undo.** Every field edit Jira accepts goes on an in-memory stack of the last 50 (status, assignee, labels, priority, dates, estimates, sprint, parent, Customer, Engagement, type, summary), and its toast says what changed with an Undo button. Two toasts stack at the bottom left over the Tree, newest last, so the last two edits each keep an Undo: `Cmd+Z` or the newest toast's button takes the newest edit off the stack, and an older toast's button takes its own edit out of the stack, so it still refuses when a later edit changed the same field. Either writes the old value back through the same mutation as the edit, so the Tree and the Peek show it at once and a refusal rolls it back. The stack ends with the session and is cleared on logout. Redo is not offered, and an undo is not itself recorded, so `Cmd+Z` again walks further back. Creates, deletes, comments, worklogs, attachments and links never reach the stack (Q38). A bulk-bar batch is one entry (see Tree).
  - An undo is refused, and its entry dropped, when the issue no longer shows what the edit set, because Jira or someone else changed it since: the toast says which field and nothing is sent. The check compares people, options and sprints by id and labels as a set, against the caches the focus refetch keeps fresh, so a change Jira made to the same field itself (automation) also refuses.
  - An edit core cannot reverse is a barrier: setting a Priority, Customer, Engagement, parent or original estimate from nothing has no "clear" in `issues:edit`. Its toast has no Undo button, and `Cmd+Z` drops it with a warning, so the stack never silently skips to an older edit.
  - A write Jira refuses on undo rolls back and warns, and its entry is dropped, so the next `Cmd+Z` reaches the edit before it instead of repeating a refusal.
  - Nothing to undo says so in a toast. Text typed in a field keeps its native undo; the app's undo never runs there.
  - A plain notice is written into one `role="status"` region that the Shell keeps mounted and empty from the start, so a screen reader announces it; the toast itself carries no live role, so its buttons are not read out with it. A refusal is an `alert` and announces itself. The same text twice in a row is announced once.

## Cell Editor

An editor anchored to a cell of a Tree or Sprint page row, for editing a property in place. The Status dot is the first cell (#267), the avatar the second (#268), the due date the third (#270), the priority slot the fourth (#269), the labels slot the fifth (#272), the Sprint slot the sixth (#273) and the start date the seventh (#271).

- **Open.** `useCellEditor(restoreFocus)` in the Shell holds the one open editor. A cell calls `open({ issue, property, cell }, pointer)` with the element that was clicked, which carries `data-pick`. The Shell renders `<CellEditor target issue issues me onClose />` beside the issue menu, with the issue read from the caches so the editor marks the current value.
- **Anchor.** `CellEditor` gives `cell` the CSS anchor `--cell-editor` and hands the editor a `CellMode` (`cell.ts`): `{ anchor, onClose }`. The editor draws no trigger, shows its popover on mount and positions it against the anchor, below the cell and starting at its left edge, flipping at the window's edges. `useShowOnMount` and `CellPopover` (`CellPopover.tsx`) are the shared parts.
- **Registering a property.** The Shell, the row and the key route by name, so a property needs exactly these:
  1. Its name in `CELL_PROPERTIES` (`cell.ts`). The name is the keymap command's name (`status`, `assignee`, `priority`, `labels`, `dueDate`, `startDate`, `sprint`), so its key routes with no Shell change: the Shell's `openCell(command, key)` opens the editor on the active row's `[data-pick="<name>"]` cell when `isCellProperty(command)`, and otherwise falls back to the Peek's picker or, for `Shift+S`, `Shift+D`, `Shift+P`, `Shift+E` and `Shift+C`, to the issue menu. A property whose key has no keymap command adds its command in `keymap.ts` first.
  2. An entry in `EDITORS` (`CellEditor.tsx`), which receives a `CellContext`: `{ issue, issues, me, cell }`.
  3. Its Tree cell: a `Pick` with that `property` in `TreeRow.tsx`. The row's click needs no change; `isCellProperty` sends it to `onCell`.
  4. Its Sprint page cell: a `Slot` (below) with `data-pick="<name>"` that calls `onEditCell(issue, '<name>', event.currentTarget)`.

- **A list editor** reuses a picker. Make the picker in `PropertyPickers.tsx` take `cell?: CellMode` and pass it on to `Picker`, as `StatusPicker` does, then register it:

  ```tsx
  assignee: ({ issue, issues, me, cell }) => (
    <AssigneePicker issue={issue} issues={issues} me={me} cell={cell} />
  ),
  ```

  Its options, queries, optimistic patch and `attemptWith` refusal toast are the ones the Peek uses.

- **A non-list editor**, such as a date field, wraps its controls in `CellPopover`. The shell opens on mount against the anchor, closes on Esc or a click outside, calls `cell.onClose` once closed, and focuses the first `[data-autofocus]` element. A control that ends the edit calls `closePopover(event.currentTarget)`. Send the change through the same write hooks and `useIssueChange` as the Peek's field. The due date is the example, and the start date is a second entry beside it:

  ```tsx
  dueDate: ({ issue, cell }) => (
    <DateEditor issue={issue} field="dueDate" label="Due date" cell={cell} />
  ),
  ```

- **Due date** (#270). `DateEditor` (`DateEditor.tsx`) holds the Peek's date `TextField` (marked `autofocus`) and, while the issue has a date, a Clear button. The field saves on Enter or when focus leaves it, never on each change, since the browser reports a valid date after every digit of the year; Enter then closes the popover. Esc drops the draft and writes nothing. A popover that closes without a blur, such as a scroll or the row leaving the window, sends a changed draft as it unmounts (`TextField`'s `commitOnUnmount`, guarded by the same `sent` check so a date is never written twice); Clear, and Esc pressed on Clear, drop the draft instead, and Tab to Clear skips the blur save. Clear, or an emptied field, sends `null`. The change is `datePatch(field, draft)` (`properties.ts`) as the write and as the optimistic patch, through `useIssueChange`, so a refusal reverts the slot and the toast offers Retry. A light dismiss is a press outside the popover, which the page sees as a pointer event. The native date picker is a separate widget of Chromium whose clicks reach no page element, so a click in the calendar does not dismiss the popover.
- **Due date on the Tree.** The whole `[data-prop="due"]` slot, filled or empty, carries `data-pick="dueDate"`, so a click opens the editor and `Shift+D` opens it on the active row. The slot keeps its column width (96px by default), and its title reads "Set due date (Shift+D)" or "Due 2026-11-03 (Shift+D)". When the Due date property is not shown, `Shift+D` opens the issue menu's field as before. On the Sprint page the slot is a `Slot` button named "Due date of PSAPAC-4: none" or "Due date of PSAPAC-4: 2026-11-03" that calls `onEditCell(issue, 'dueDate', event.currentTarget)`, so Enter or Space opens the editor and focus returns to it. `Properties` takes `onEditCell` for this; without it the slot is drawn only.
- **Start date** (#271). The `startDate` entry of `EDITORS` is the same `DateEditor` with `field="startDate"` and label "Start date", so Save, Clear, Esc and the refusal toast ("Start date not changed", with Retry) are the due date's. The `Properties` slot is `StartDate` in `TreeRow.tsx`: `[data-prop="start"]` with `data-pick="startDate"`, a slot with no icon and no tone, at the column's width (96px by default), titled "Set start date (Shift+S)" or "Start 2026-10-01 (Shift+S)". `Shift+S` opens the editor on the active row when the Start date property is shown, and the issue menu's field otherwise; on the issue page it focuses the page's field (`aria-keyshortcuts="Shift+S"`). On the Sprint page the slot is a `Slot` named "Start date of PSAPAC-4: none" or "Start date of PSAPAC-4: 2026-10-01". The property is `start` in `ROW_PROPERTIES` and `startDate` in `CELL_PROPERTIES`, as `due` and `dueDate` are. A start date after the due date is allowed.
- **Close.** Esc, a click outside, a choice, a scroll of anything that holds the cell (ignored for the first two frames, since the click may have scrolled its row into view) or the cell leaving the page closes the popover, and `onClose` removes the editor. If focus went with it (Esc, a choice), `restoreFocus` returns it to the Tree or the page that was focused after two frames, when a choice has moved its row; a click that put focus on another control keeps it there.
- **Reveal.** A click on a cell, and `S`, first scroll the row into view through `IssueTree`'s `reveal` (the step a keyboard move uses), so a row clipped at the Tree's foot or head opens its popover against a cell the user can see. The Shell reaches it through the `control` ref.
- **Toggle.** A press on the cell whose own popover is open closes it, and the click that follows must not open it again; `cellReducer` remembers that press (`pressed`) and swallows the click. A press released away from its cell is forgotten a frame after the release. A key (`pointer: false`) always opens.
- **Tree.** A click on the status dot or the avatar makes the row active and opens the editor. It does not open the Peek, arm the double-click, change the checked rows or select text; `Shift+click` still checks a range. `S` and `A` on the Tree open the editor on the active row's dot and avatar. An unassigned row's dotted person is a target too. The row keeps its drag.
- **Sprint cell (#273).** The Tree's Sprint slot (`data-prop="sprint"`, shown while the Sprint Display property is on) carries `data-pick="sprint"` on a Story, Task or Bug, filled or empty, and opens `SprintPicker` with its Backlog and sprint options, `sprintPatch` and refusal toast. An Epic or a Subtask (`propertyRules(...).sprint`) gets no `data-pick`, and on the Sprint page the slot is a `Slot` button with `data-pick="sprint"`, named "Sprint of PSAPAC-13: Sprint 5" ("Backlog" when empty) and titled with the full name and end day, which `Properties` draws when `SprintPage` passes `onEditCell`. A move to another sprint, or to Backlog, takes the row off the page at once (`leaveSprints` in `optimistic.ts` removes the issue from each Sprint page read whose sprint the patch's `sprints` no longer lists), a refusal puts the copy back (`Rollback.left`), and with the row gone focus falls to the Sprint page through `restoreFocus`. A filled slot keeps the full name and end day as its title; an empty target's title is "Set sprint". The list names each sprint in full with `sprintDetail` beside it: the end day as the slot shows it (`18 Oct`, with `'25` in another year), `Closed` for a closed sprint, else the state. The issue page, menu, create dialog and bulk bar pickers use it too. `Shift+C` on the Tree opens the list when the slot is drawn, and the issue menu's Sprint picker when it is not: the Sprint property is off, or the Tree is too narrow to show its slots (an open Peek does that), where `openCell` finds the cell hidden (`checkVisibility()`). A Hold row stays editable.
- **Sprint page.** The status cell is a `Slot` at the left of the row's content, named "Status of PSAPAC-4: In Progress". The assignee cell is a `Slot` around the avatar at the end of the row's content, inside the faded span so a Hold row keeps its fade, named "Assignee of PSAPAC-4: Test User" or "Assignee of PSAPAC-3: Unassigned". Both are in the tab order, so Enter or Space opens the editor, and the row button still opens the issue. `optimistic.ts` patches, rolls back and cancels reads of the Sprint page's own copies of the issue (`['sprint', id]`) with the lists, so the row changes group at once and a refetch cannot bring the old value back.

- **Slots.** A Sprint page row holds its controls beside the button that opens the issue, never inside it, since a button cannot hold a control (axe's `nested-interactive`; a screen reader treats a button's children as text). `li[data-issue-key]` is `relative` and holds, in this order:
  1. The open-issue `<button data-row>`, `absolute inset-0` with `aria-label="PSAPAC-4 <summary>"`. It is the first tab stop and takes the row's click, its right-click and `Shift+F10`.
  2. A `div` of the row's content, `pointer-events-none relative`. A click on text or empty space falls through it to the button below. The Hold fade is one `span` in it (`holdFade`); the status slot and the pencil sit outside that span, so their focus rings are never faded. A slot inside the span keeps its ring in full too: while one has `:focus-visible`, `styles.css` takes the fade off the span and puts 30% on each of its children but that slot, so every other part stays at 30% (`e2e/desktop/holdfade.test.ts`).
  3. Each control in the content is a `Slot` (`Slot.tsx`): a real `<button type="button">` with `pointer-events-auto`. `SLOT` is the same class, for a control that is not a button, such as the estimate field while it is open.

  A story that adds a Sprint page target makes it a `Slot`, in the place the cell already has:
  - **Time cells** (`TimeCell`, `EstimateCell`) already take `always` and draw a `Slot` in place of their Tree `<span>`.
  - **Labels and sprint** are cells of `Properties` (`TreeRow.tsx`), which passes `always` only to the time cells. Pass it to the cell, and draw the `Slot` when it is set. `DueDate` and `StartDate` already take `always` and `onEditCell`.
  - **Assignee** is the `Avatar` in `SprintPage.tsx`, outside `Properties`, wrapped there in a `Slot` (#268).
  - **Priority** is a `Slot` that `SprintPage.tsx` draws itself, after the summary and before `Properties`, around the Tree's `PrioritySlot` glyph (#269).

  `Properties` takes `onEditCell` (added by #270, which `SprintPage` passes) and a cell draws its `Slot` when `always` and `onEditCell` are both set. `DueDate` is the example, and the Sprint cell (#273) takes it the same way. The labels cell (#272) reads:

  ```tsx
  return always ? (
    <Slot
      data-prop="labels"
      data-pick="labels"
      aria-label={`Labels of ${issue.key}: ${issue.labels.join(', ') || 'none'}`}
      onClick={(event) => {
        onEditCell(issue, 'labels', event.currentTarget)
      }}
      className={CLASSES}
    >
      {chips}
    </Slot>
  ) : (
    <span data-prop="labels" className={CLASSES}>
      {chips}
    </span>
  )
  ```

  Give it an accessible name (its text, an `aria-label` or a `title`), keep it a direct control of the content and never put one inside another. A control that opens an editor calls `onEditCell(issue, '<name>', event.currentTarget)` and focus returns to it. The row button is described by the `Properties` values (`aria-describedby`), so a keyboard user hears them on arriving at the row. Tab order follows the visual order: the row button, Status, Priority, the property slots in the Display menu's order, then the pencil. `slots.test.ts` fails when a control nests in another.

- **Assignee.** The list is the Peek's `AssigneePicker`: Unassigned, Me, recent assignees and a search of assignable users, named "Assignee", with its optimistic patch and Retry toast. Esc closes it with no write.
- **Priority.** The priority slot on a Tree row is a `Pick` with `data-pick="priority"` (`PriorityCell` in `TreeRow.tsx`), a target whether the slot draws bars or is empty (Medium or no priority). The slot keeps its 16px (`size-4`, `data-slot="priority"`) inside the `Pick`'s padding and negative margin, so columns do not shift, and an empty slot shows a faint outline on hover. `PriorityPicker` takes `cell` and opens as "Priority"; `P` on the Tree opens it on the active row's slot. A choice writes through `useIssueChange`, so the bars change at once and a refusal reverts them with a Retry toast. A Hold row stays editable and its slot keeps the row's fade. On the Sprint page the slot is a `Slot` named "Priority of PSAPAC-4: Medium" ("none" when unset), with `data-pick="priority"` and `aria-haspopup="listbox"`; it calls `onEditCell(issue, 'priority', event.currentTarget)`, is in the tab order between Status and the property slots, keeps the 16px glyph slot, and sits inside the row's Hold fade like the property slots. Enter or Space opens the list and Esc returns focus to the slot. The Peek's Priority picker, the issue page's and the palette's "Change priority" are unchanged.
- **Labels.** The Tree's labels slot (`[data-pick="labels"]`, the whole slot (96px by default), filled or empty) opens `LabelsPicker` in the cell editor, and `L` does the same on the active row. The picker is a multi-select, so a choice leaves the list open and each toggle writes at once; Esc or a click outside closes it. `openCell` falls back to the Peek's picker when the slot is not drawn (`checkVisibility()`): Labels is off in Display, or the Tree is too narrow. On the Sprint page the same cell is a `Slot` button named "Labels of PSAPAC-4: none" that calls `onEditCell(issue, 'labels', event.currentTarget)`; it is in the tab order and Enter or Space opens the list.

## Create and Delete

- `C` opens the create modal (see Keyboard for the rules every letter shares). It is off until the Tree has loaded. The New issue button in the Issues header does the same, so the shortcut has a visible alternative.
- The form starts as a Story (Q33), except under `C` (#224), which starts it under the issue the pointer rests on, else the active row: a hovered row wins, as in Linear, read from CSS `:hover` when `C` is pressed, so hovering selects nothing and opens no Peek. A Tree navigation key (`J`, `K`, the arrows, `PageUp`, `PageDown`, `Home`, `End`, unmodified and pressed in the Tree) ends a hover, so a row scrolled under a resting pointer does not override the active row; moving the pointer or turning the wheel brings the hover back. An Epic gives a Story under it; a Story, Task or Bug gives a Subtask under it; a Subtask gives a sibling Subtask under its parent. A hovered Customer header or chip counts for nothing, and the New issue button, the page's `C` and a chip keep the Story. With an issue selected (the active row, a "N done" chip's open parent, or the page's issue) the parent is the nearest Epic at or above it, the Epic itself when an Epic is selected. Customer and Engagement come from that Epic, else from the selected issue: the Epic wins, so a new Story does not start as the Customer mismatch Q15 flags. A Customer header supplies its Customer alone. The assignee starts as the current user (#237), from every entry; when the current user loads after the dialog opens, the form takes it unless an assignee was already chosen, Unassigned included. Sprint, priority, labels, estimate, Start date and Due date start empty. Changing the type keeps a parent that still fits and otherwise takes the type's own default: a Subtask goes under the selected Story, an Epic has no parent.
- Summary, Customer and Engagement are required on every type, Task and Bug included (Q14), and a Subtask needs a parent. The Create button stays disabled and a line under the form says what is missing. An Epic has no parent, sprint or estimate; a Subtask has no sprint (`propertyRules`). The create form is a Type icon beside the summary and a strip of chips, each the page's own `Picker` fed by the same hooks. Type shows only its icon until opened, then lists every type. Customer and Engagement are accent-tinted chips that read "Required" in red until chosen; Parent searches by issue key or words and, on a Subtask, is a tinted chip that reads "Required" until chosen; "+me" beside Assignee sets the current user and hides while that is the assignee; Estimate is a chip with a field in it. Start and Due are chips with a native date input each, the same `type="date"` input the issue page's Dates and time section uses, both optional and on every type. The create sends a date it holds as `startDate` and `dueDate`, and core puts the Start date under the field it resolved by name. A Due date before the Start date shows no warning, as on the issue page. The dialog is 42rem wide (672px) at any window width, so the chips wrap onto a third row. A date typed only in part ("10/yyyy") reads as empty to the browser, so the field shows in red, the line under the form says "Add a complete Start date to create." (or Due date), Create stays disabled and Cmd+Enter focuses the field. On Cmd+Enter with the form unready, focus goes to the first missing field (summary, parent, Customer, Engagement, estimate, the form's order, since a parent fills Customer and Engagement) and nothing is sent. Choosing a parent whose Customer or Engagement differs opens the Q16 prompt, which here says "Move this issue under". With no Customer or Engagement chosen yet, the parent's values start the form without a question.
- The form also has a description editor under the summary, the page's own `AdfEditor` in its `embedded` mode (no border or Save row of its own), and an Attach files button that lists the chosen and dropped files with a bin button each. An image pasted into the description, or dropped on it, is staged: the placeholder shows a preview and "<name> uploads when the issue is created" with a Remove button, and nothing is sent until the issue exists (see below). Cmd+Enter in the editor creates, and Esc closes the dialog. A description with no visible text (Enter, Shift+Enter, spaces, an empty heading or list item) is not sent. The editor is `inert`, and dimmed, while the create is in flight, since a contenteditable ignores a disabled fieldset.
- Create sends `issues:create`, with the typed ADF description in the request. Core's `createIssue` makes the issue and reads it back; main then moves it into the chosen sprint, since core's create takes none, and reads it again. The form stays locked, and Esc does nothing, until Jira answers. The read-back goes into the cache of its phase and the Tree selects it, opening any collapsed Epic or Customer above it first; no list is reloaded. A filter that hides the new issue leaves the selection where it was.
- PSAPAC's automation rewrites new issues, so the notice after a create compares the form with what Jira holds: it names the key and summary, then each of Customer, Engagement, Parent, Sprint, Original estimate, Start date and Due date that differs ("Customer is Collibra (Internal team) (you chose Acme)") and any label Jira added. A failed step after the create (the sprint move, a read-back or an attachment) is a warning on the notice, which stays until dismissed; the issue exists either way. The chosen files attach after the create, one at a time through the page's own `attachFiles` and `attachments:add`, while the dialog shows "Attaching" and stays locked. With "Create more" a file that failed also takes a toast, since the next create overwrites the line in the modal; the toast has an Open button only when the issue was read back. A file that fails (empty, over 100 MB, or refused by Jira) adds a note "Could not attach NAME to KEY." with the reason, and the other files still go up. When the read-back failed the unresolved list reloads to show it.
- The automation lands after that read: estimates within about 1 s, the label, Customer, parent and sprint within about 10 s. With a window to tell, `issues:create` also schedules a second read of the new issue after `LATE_READ_MS` (10 s; the `lateReadMs` backend option shortens it in tests). Main sends it as the `issues:lateRead` event, which preload exposes as `onLateRead`. The Shell keeps the form and first notice of each create, puts the late read into the Tree and any open page, and shows a second toast, "Jira changed PSAPAC-N after it was created", with the fields that differ from the form and that the first notice did not name. It shows nothing when nothing is new. While an edit of that issue is in flight the late read is not put into the caches, since it would bring back the old value over the edit's own; the edit reads the issue when it settles, and the toast still shows. Logout and quit clear pending reads; a read is skipped when the window is gone and dropped when the issue is gone. Quit waits for the settings and views writes queued so far.
- After the create, the dialog stays locked and runs three steps in order, each on the new issue: it uploads each staged image one at a time through `attachments:addImage` (which also resolves the image's Media Services id from the content redirect, as on the page), writes the description again through `issues:setDescription` with every uploaded image in its `mediaSingle` where it was pasted (the create itself sends the text only, with the images taken out by `fillImages`), then attaches the chosen and dropped files. The write is checked against the description Jira holds for the new issue (the create's read-back, else what was sent), so a description someone changed in between is not overwritten. A failed image upload leaves that image out and does not stop the next; a refused write or a changed description leaves the uploaded images on the issue as attachments. None of these undoes the issue: the notice names each failure with the key, stays until dismissed, and also reaches a toast under "Create more". The write records no undo step, so Cmd+Z does not take the images back out. The placeholders keep their "Uploading" figure through these steps (a finished image is not loaded back into the dialog, since it has no issue key to load under) and all go once they finish, including any the user deleted from the text meanwhile. An image pasted from the clipboard is named `pasted-1.png`, `pasted-2.png` and so on, keeping its extension, so a failure notice says which one; the numbering restarts at `pasted-1` after each Create more, and a dropped file keeps its own name. A staged image whose upload failed shows its failure with Remove only and no Retry, since the dialog is locked and the notice names the failure afterwards. If a step throws after the create, the notice says so and the create still ends, so a second Create cannot make a duplicate. The dialog registers the new issue with the Shell the moment the create succeeds, before any upload, so the late read of PSAPAC's automation (about 10 s) is reported even when the uploads take longer. The pure steps are `fillImages`, `pastedImages` and `embedPasted` (`createImages.ts`); the staged images live in the `uploads.ts` store under `STAGED_KEY` until `commitUpload` sends them, and closing the dialog removes any left.
- Files dropped on the dialog stage like the Attach files button. The dialog has two zones that light up with their own labels while a file is dragged over the window (`useFileDrag`, as on the issue page): the description ("Add images into description": an image goes into the description, any other file stages) and the chips and Attach files rows ("Attach files to the new issue": every file stages). A drop anywhere else on the dialog, such as the title, stages everything. `DropZone` claims the drop, so the dialog's own handler skips it, and the dialog is not inside the issue page, so a drop on it never reaches the page's handler even when the dialog was opened from a page. A drop while the create is in flight is ignored.
- "Create more" keeps the modal open with everything but the summary, the description (with its pasted images) and the chosen and dropped files, shows the notice inside the modal (the Tree behind it is inert) and focuses the summary. Cmd+Enter creates from anywhere in the form, or focuses the first missing field.
- **Sub-issues from the page (#145).** A Story, Task or Bug page has a Subtasks section whose heading shows done over all ("2/5", from each subtask's status category) and a "+" (Add sub-issue). The "+" opens a form with one box: one title per line, blank lines ignored, nothing else changed (list markers stay in the title). Create (or Cmd+Enter) makes one Subtask per title through the same `issues:create` the dialog uses, under the page's issue with its Customer and Engagement; a parent lacking either is told to set it first. There is no new IPC channel. At most 50 titles of 255 characters each. The creates run one at a time in the order pasted, because each is a write to Jira, the Subtasks then come out in order, and a refusal leaves a clean boundary. Each one joins the Tree lists and the page's subtask list the moment Jira answers (the page's subtask list is patched from the create's read-back, so a read that began earlier cannot hide it), and the count follows. The run stops at the first refusal: what was created stays, the box keeps the title that failed and every title after it, and a sticky notice says "Created 3 of 5 sub-issues under PSAPAC-32", names the title and Jira's reason, and says how many were not tried. Create then sends only what is left, so a created title is never sent again. A create that fails with `jira_error` (the network failed, the request timed out, Jira answered 5xx or sent a reply core could not read) or `internal` may have reached Jira, so the run reads the parent (`issues:get`) before it stops or retries. A Subtask whose summary equals the title exactly (`landedKey`, `subtasks.ts`) and whose key was not among the parent's Subtasks when the run began, nor made or confirmed earlier in it, counts as created: it joins the lists, the notice says it reached Jira although its reply was lost, and the run goes on to the next title. Otherwise the title fails as a refusal does and Create sends it again. If that read fails, or the page had no Subtasks list at the start of the run to compare with, the title stays in the box and the notice says it may already exist and to check the Subtasks before creating it again. A `validation_failed`, `not_found` or `permission_denied` refusal, and an error thrown before the send, trigger no read. The rule cannot tell a Subtask someone else added with the same summary during the run, or since the page last read the parent, from this one. An Epic takes no Subtasks and a Subtask cannot hold one (`fitsParent`), so those pages show no "+" and no section. Each created Subtask still schedules main's 10 s late read, which the Shell ignores because no dialog draft is waiting for it, so the automation's changes are not applied to the section and a 50-title paste makes up to 50 extra reads.
- The delete confirmation opens from the Delete button on the Peek and on the page; there is no key for it. It reads the issue afresh (`issues:get`) and lists every subtask Jira deletes with it, which the confirm button names ("Delete issue and 2 subtasks"). Confirming a list of subtasks is the choice to cascade; with none, the delete sends no cascade. Cancel has focus, so Enter never deletes, and Esc or Cancel returns focus to the Delete button. Child issues that are not subtasks, such as an Epic's Stories, are not deleted: the dialog says they lose their parent and names the first five.
- Delete is optimistic. The dialog closes at once, the issue and the subtasks chosen leave both lists, the children that stay lose their parent, and the page or Peek that showed it closes. A refusal puts everything back and the notice says so; a success says what went. No issue is read afterwards, so the next focus refetch of the unresolved list reconciles; a phase still on its first load starts again when the deleted issue was in no loaded list, since that load may have paged past it. The dialog holds the issue it was opened for, so it neither depends on the lists holding it (a Done parent opened from a child's page before Done loads) nor closes if a refetch drops it. `issues:delete` reads the subtasks again and refuses to delete an issue that has subtasks without the cascade, and refuses a cascade to a subtask the user was not shown, so one added since the dialog opened is never deleted unseen.
- The modals are native `<dialog>` elements through `Modal`: the page goes inert, Tab stays inside, Esc closes, and focus returns to the control that opened it, or to the Tree when that control has gone.

## Saved Views

- The sidebar's Views section lists `views.json`, the file `jm view list` and `jm issue list --view` read. Core's `createView`, `renameView`, `deleteView`, `updateView`, `duplicateView` and `moveView` do the work in main, so a view made here shows in the CLI and the reverse. Before the file exists the list shows the starters, "My issues", "Created by me", "Current sprint", "Active" (In Progress, Review) and "Backlog" (Opportunity, To Do, Hold); they are ordinary views once the first change writes the file, so they can be renamed, reordered and deleted, and a starter added later reaches only a user with no file.
- The views also show as tabs over the list (`ViewTabs.tsx`, group "View tabs"), in the same order. A tab is a ghost `.btn` (28px, 6px radius, so it differs from Linear's full pill, which the button audit refuses), applies its view and is marked like the sidebar row.
- Each row has Update (check), Duplicate, Rename and Delete buttons that show on hover or focus. Update replaces the view's filters, toggles and display with the current ones and keeps its id, name and place; it is disabled while the bar and the display already equal the view's (a view with no display holds the defaults). Duplicate adds `<name> copy` (then `copy 2`) just after the original and focuses it. Neither is optimistic, since a refusal changes nothing. After an Update, focus returns to the view's apply button, because the Update button disables once the bar equals the view.
- Reorder by dragging a row onto another (native HTML drag and drop, with the custom type `application/x-jm-view` and no `text/plain`, so a text field has nothing to take from a dropped row; an e2e reads the types from the `dragstart`), or with Alt+Up and Alt+Down on a focused view. The view takes the index of the row it is dropped on. The change is optimistic, writes the array order through `moveView`, and a refusal puts the old order back. Focus follows a view moved by key. The order is the array in `views.json`, so it survives a restart and `jm view list` prints it.
- Clicking a view replaces the filter bar's filters with the view's, sets the three toggles to the view's and, when the view has a display, sets the display to the view's too (a view with none leaves the display as it is). The toggles go through the same write as a press on a toggle button, so they are written to `settings.json` and stay as the view left them after a restart (Q28: each toggle remembers its last state). The filters last for the session, as before.
- The view that equals the filter bar and the toggles is marked (`aria-current`). Of several twins, such as a duplicate and its original, the view applied last is the one marked (Shell holds its id and forgets it once the view leaves the list, so a new view with the same id is not lit), else the first. It is derived on each render, so it stops being active the moment a filter or toggle changes (display does not count: toggling a property keeps the view lit), and a bar built by hand that matches a view marks it.
- Issues in the sidebar is highlighted (`aria-current="page"`, fill and weight 500) only when no saved view matches and none of the Inbox, a sprint page, the Epics table or the Customers page is open; while one of those is open it alone is lit, so one item is lit at a time. Neither draws a bar or an edge.
- New view (the + beside the heading) saves the current filters, toggles and display under a name typed inline. Enter saves, Esc cancels, and a taken or empty name keeps the field open with core's message. Core makes the id, a slug of the name, so the row appears when the write answers.
- Rename is an inline field (pencil button, or F2 on a focused view): Enter or leaving the field saves, Esc cancels, and the id stays. Rename and delete are optimistic: the list changes at once and a refusal puts the old name or the view back and shows the error under the list. Delete asks inline, in place of the row, with Cancel focused; Esc cancels. Focus goes back to a view button afterwards.
- Up and Down move between the views. There are no single-letter shortcuts.
- Main runs every views call through one promise chain, since core reads, changes and rewrites the whole file and two overlapping calls would drop an edit. There is no lock file: the CLI only reads `views.json`. A CLI command that writes views must lock the file first, as core's timer does for `timer.json`.
- A view is read again on window focus, so a hand edit of the file shows up when the window regains focus.

## Inbox

- The sidebar's Inbox link opens a page over the Tree, as an issue page does, and shows a count of unread entries beside it. The link is `aria-current` while the page is open, and the Issues link, a saved view, a sprint entry or the palette's Go to view leaves it. While it is open the Tree is inert and the Tree's letter keys do nothing. The palette and the shortcut help return focus to the control that opened them, and into the Inbox (`restoreFocus`, by the open surface) when that control has gone, such as an entry that left the list. The Filter menu key (`F`) does nothing under the Inbox, a Sprint page or an issue page.
- The page lists the issues the user is assigned to, reported or watches that changed in the last 14 days (core's `listInbox`), newest first. An unread entry has a dot, a bold title and a second line naming the newest change by someone else after the read mark: `PSAPAC-3139 · Status: To Do to In Progress · Sharon Warner`, or `PSAPAC-2477 · Comment by John Shea`. A read entry is muted and says where the issue stands: `PSAPAC-3139 · In Progress`. The age on the right is the change's, or the issue's `updated` when it is read. The ages are as of the last read of Jira.
- Opening an entry (click or Enter) marks it read up to the `updated` time the entry showed, and opens the issue page above the Inbox. Back returns to the Inbox. A change that lands after that time leaves the entry unread. Mark all read marks everything up to the newest `updated` in the list; the button is disabled with nothing unread. Both show the result at once and write `inbox.json` through `inbox:markRead` and `inbox:markAllRead`; a refused write puts the marks back and says so. Up and Down move between entries.
- The marks are `inbox.json`, whose shape is in [Config](../../docs/reference/config.md#inboxjson). An issue whose changes since its mark are all the user's own is read, so editing an issue in the app never makes it unread.
- Main reads and writes the file through one promise chain, as it does for views, since core reads, changes and rewrites the whole file. The CLI neither reads nor writes `inbox.json`, so there is no lock; a `jm inbox` command that writes it must lock first. A second `inbox:list` while one runs shares its answer. Core's cache keeps each issue's changelog while its `updated` stays the same, so a poll sends one search and nothing more when nothing changed. Logout aborts the load and drops the cache.
- The Inbox is read on login, on window focus (through the same focus bridge as the Tree) and every five minutes (`INBOX_POLL_MS`). TanStack Query starts no second fetch while one runs, so a poll that falls on a running read is skipped. The badge needs the Inbox loaded, so it appears a moment after the Tree.

## Sprint Page

- The sidebar's Sprints section lists Current, the active sprint, and Upcoming, the next future sprint that has dates (the picker's Q20 rule, `sidebarSprints`), each with the sprint's name. An entry with no sprint is disabled. Both read `sprints:list` under the Sprint picker's query key, so the sidebar and the picker share one read.
- A sprint also opens from an issue page: an Open button beside the Sprint value (`Open sprint <name>`) shows while the issue is in a sprint, and replaces the issue page with the sprint page. The Peek has no Sprint row, so it has no link.
- The page covers the Tree as the Issue page does: the Tree and the Peek stay mounted and inert under it. A sprint's issue opens its page above the sprint page, and Esc or Back returns to the sprint. The sprint page is inert under an open issue page, so Tab and Shift+Tab never reach it, and it takes focus back when the issue page closes. Esc, Back to issues, the Issues link and applying a saved view leave the sprint page, and focus goes to the Tree. It takes no letter shortcuts.
- The left side lists the sprint's issues by status in the Tree's status order, each row a status slot, a key, a summary, a priority slot, the row properties the Display menu chose (the same slots as the Tree, shown at any width, each with a visually hidden label; they wrap onto a line of their own when the summary would have under `10rem`), the assignee and a pencil. A click on the row outside those controls opens the issue. Each of those controls is a separate button beside the row's own, not inside it (see Cell Editor, Slots). The rows are at most `40rem` wide with no property on and `64rem` otherwise; the heading, the "N issues" count and the group headers stay at `40rem`. One header row of property names (`[data-column-names]`, drawn only, no resize) sits above the first status section and each slot takes the width set in the Tree; a row that wraps its properties onto a line of their own no longer lines up with it. An empty sprint says "No issues in this sprint."
- The right panel shows Status, Start and End as local days, the Goal ("No goal set" when empty), and Progress. Scope is every issue in the sprint. Started is the issues whose status category is In Progress, and Completed the issues whose status category is Done, whatever the status is called. Each shows its percent of Scope. The progress bar is Completed in the done colour, then Started in the in-progress colour, on a `--line` track (`role="progressbar"`, value Completed's percent).
- The tabs are Assignees, Labels, Priority, Customer and Engagement. A row reads "N% of M": M issues share the value, and N percent of them are Completed. Rows sort by M, then name; the issues with no value come last as Unassigned, No label, No priority, No Customer or No Engagement. An issue with several labels counts under each. Arrow keys, Home and End move between the tabs and select as they go.
- No coloured border marks any of it. The open sprint's sidebar entry is the one lit item, by the `is-current` fill and weight; Issues and the saved views give theirs up while a sprint page is open, and the selected tab takes the same fill.
- `sprints:get` takes `{ id }` and answers `{ sprint, issues, stats }` from core's `readSprint`: the sprint (with its goal) and every issue in it, read page by page from the Agile sprint endpoints and validated. It only reads, and core counts (`sprintStats`), so the CLI could show the same numbers. The page shows its last copy at once and reads again on each opening (ADR-0002). An open Sprint page also refetches when any issue changes: `applyFreshIssue` (every edit re-read, create read-back and late read), a delete, and the paths where a re-read or a create read-back failed all mark the sprint reads stale. Logout removes them.
- Not built: the burndown line.

## Epics and Customers

- The sidebar's Epics and Customers links open a page over the Tree, as the Inbox does, and are lit (`is-current`, `aria-current="page"`) while open. One page at a time: opening the Epics table, the Customers page, the Inbox or a sprint closes the others. The Shell holds one `overview` state (`'epics' | 'customers' | null`) that joins `covered`, so the Tree is inert, `/` and `F` do nothing, the palette lists no actions and `restoreFocus` returns to the page (`overviewRef`). An issue opened from either page opens above it, the page is inert beneath, and Esc returns to it with focus on the row opened. Esc, Back to issues, the Issues link and applying a saved view leave for the Tree.
- Both pages place their own focus, as the Inbox does: on the row last used, else the first row, else the page. Up and Down move between rows. The pages take no letter shortcuts.
- Progress is done over total of an issue's direct children (core's `childProgress`: the issues `buildHierarchy` nests under it, an Epic never being a child), Done by status category. It counts the loaded issues whatever the toggles and filters hide, so with "Hide done" on a pill still counts the Done sub-issues the Tree no longer shows. Until the Done phase loads the counts hold only open issues, and the pages say "Loading Done issues, so counts may grow." If the Done load fails, the pages and the Tree stand in for the banner the covered list holds: the frame shows "Could not load Done issues. Done counts are hidden." with Retry, the pill goes from the Tree rows and the issue page line, the Epics table's Issues and % done cells and the Customers page's % done read "Not loaded", and Open stays, since it counts open issues only. Before the open issues load the pages show "Loading issues", and if that load fails the same error and Retry the Tree shows, never "No Epics." or zero counts. The focus is placed once each time the page comes to the front, and on the first row if rows arrive late and focus has not moved on.
- A Story, Task or Bug Tree row with at least one sub-issue ends its title with the pill (`3/8`, a ring that fills clockwise; #200 moved it from the Epic rows). The row's accessible name ends with "3 of 8 done". An Epic row, a Subtask row and an issue with no sub-issue show none (`rowProgress` in `TreeRow.tsx`). The Epics table keeps its % done column. The issue page's "Sub-issue of" line sits under the title: the parent's type icon, key, summary and its pill, which opens the parent. It replaces the page header's "in KEY" link, so the parent has one link. The line adds one row, so the description starts by y=164 under it and still by y=140 on an Epic page.
- The Epics table lists every loaded Epic, Done ones once their phase loads. A header button sorts by its column (`aria-sort` on the `th`): the Epic key and the % done and Issues columns and Priority start high to low, Customer, Status, Assignee and Due date start low to high, and a second click reverses. Status sorts in the Tree's order. A missing Customer, Priority, Assignee, due date or % done (an Epic with no issue) sorts last in both directions, and ties go newest key first. The default is the key, newest first. The table reads the issue caches, so an edit made on an Epic's page shows in it at once. Issues is the Epic's direct children and % done is done over that total.
- The Customers page lists every Customer option of the Project (the Customer list, which the page asks for and the session then keeps) plus any Customer an issue names that the list lacks, sorted as the Tree's groups are (internal Customers last). Open is the Customer's own open issues, Epics included, by the issue's own Customer field, so a Story under another Customer's Epic counts for its own. % done is Done over all of them; a Customer with no issue reads 0 and "No issues". An issue with no Customer counts for none. A row sets the filter to that Customer alone (`customer: [name]`, replacing the others) and shows the Tree, which under the default toggles (Hide done on) holds that many open issues, plus the Epic of a child with another Customer as context; A Customer with no issue opens an empty Tree with its Clear filters button. If the Customer list fails to load, a banner with Retry says Customers with no issue are missing.
- No coloured border marks either page. Not built: a Customer's own page, a "No Customer" row and a table for Customers that sorts. Epic rows show no progress ring, by #200; an Epic's progress is its % done in the Epics table.

## Activity

- The page shows, under the subtasks: Links, Worklogs (not on an Epic), Activity (the comments and the comment box) and Attachments last. Each reads on its own (`comments:list`, `worklogs:list`, `links:list`, `attachments:list`), so one failing shows its error and Retry and leaves the others. They load when the page opens and again on window focus. Logout removes them.
- Comments use `AdfEditor`: a read-only editor for each comment, switched to edit mode by **Edit comment**, and an always-open editor for the comment box (`saveLabel` "Comment", `cancelLabel={null}` so no Cancel button shows and Esc cancels, `autoFocus` off). Only the author sees Edit and Delete. An edit is not optimistic: the editor stays open, reads "Saving" and keeps the text when Jira refuses. An empty comment is refused. Delete asks inline, removes the comment at once and puts it back when Jira refuses. Images dropped on a comment editor embed as in the description. Unsaved text, in an edit or in the comment box, is a draft in `drafts.ts` beside the description's: leaving the page keeps it, coming back reopens it, and it holds a quit and a logout like the description's does. Saving an edit reads the comments again first: if Jira's comment no longer matches the one the edit began on, the row asks **Save mine anyway** or **Discard mine**, as the description does, and sends nothing until the user chooses. A comment list read drops the draft of any comment it no longer holds, so a comment deleted in Jira stops counting in the quit and logout prompts.
- Worklogs: a duration (typed naturally and sent as a Jira duration, `parseDuration`), a start and an optional one-paragraph comment. Add takes a date, today by default, and starts at that day's current time of day; edit keeps a `datetime-local` start. Core sends `adjustEstimate=auto`, so the remaining estimate falls by the time logged, moves by the difference on an edit and returns on a delete; the page reads the issue once afterwards, so the sidebar shows the new estimate and Time remaining. An edit sends only the fields that changed, and cannot clear a comment. Add and edit are not optimistic; delete is, after an inline confirmation. The author alone edits or deletes.
- Links: the add form has one select of types read in a direction ("blocks", "is blocked by"), Q19's five types first and the rest below under their own group, and a key field that suggests the loaded issues. `outward` makes this issue the blocker of a Blocks link, which core sends as `inwardIssue`. `links:add` refuses an issue outside the settings project at either end and a link to itself; `links:remove` reads the link, requires it to touch the page's issue and refuses an end outside the project. Add is not optimistic (Jira answers with no body, so the list reads again); remove is. A linked issue opens when it is in the loaded list.
- Attachments: every file of any type, with size, author and date. **Download** sends the attachment id; main checks it belongs to the issue, opens `dialog.showSaveDialog` (Downloads, the attachment's name with unsafe characters made `_`), then reads the bytes with `redirect=false` (up to 100 MB, held in memory) and writes them to the path the user chose. The renderer never names or receives a path. The name is cut to 255 UTF-8 bytes with its extension kept. `pnpm package` sets `LSFileQuarantineEnabled`, so macOS quarantines what the app saves, as it does a browser download. Cancelling the dialog writes and fetches nothing. **Attach file** opens the native picker.
- A file dropped on the page attaches (`useAttach`, one at a time, queued, each file to the issue it was dropped on even after the page moves to another): on the Attachments zone, on the description when it is not an image, or anywhere else. `DropZone` claims each drop it takes, so the page-level handler skips it; when an editor embedded images from a drop, only that drop's other files attach. Images dropped on the description or a comment editor embed and also appear in the list. A file that is empty, over 100 MB or unreadable (a folder) is reported and skipped; a failed upload never stops the next.
- Not built: removing an attachment, comment mentions and reactions, and Jira's change history. Comments, worklogs, links and attachments are not on the undo stack.

## IPC

- Add a channel in three places: the `IpcContract` entry and the `CHANNELS` list in `src/shared/ipc.ts`, a zod schema in `argSchemas` and a handler in `createHandlers` in `src/main/handlers.ts`. The compiler fails when one is missing.
- Every handler returns `{ ok: true, data }` or `{ ok: false, error: { code, message } }`, the core error shape. A thrown `Error` loses its fields crossing IPC, so nothing throws across it. An error that is not a `JiraMgrError` becomes `internal` with a fixed message.
- The renderer never fetches an image. `avatars:get` returns checked bytes, the renderer makes a blob URL, and the CSP allows `blob:` but no remote host.
- Main answers only the main frame of one of its own windows while that frame shows the app's page (`src/main/trust.ts`). It refuses every permission request from the page, such as notifications and camera.
- Main validates every argument at the boundary. The schemas check shape and length; core owns the deeper rules and answers `validation_failed`.
- The token goes renderer to main once, at login, and stays in main. No channel returns it, and no error message or log line carries it, with `JM_DEBUG=1` too, which logs stack frames and never the message. The login mutation has `gcTime: 0`, so the cache drops the token with the login screen. Until then it sits in the renderer's memory, as the typed value does.
- Each handler gets a second argument, `{ sendProgress, isOpen, sendLateRead }`, built from the requesting window's sender. `issues:list` reports each page through it as the `issues:progress` event, which preload exposes as `onIssuesProgress`. The renderer numbers every load and ignores progress for any other load id.
- `issues:searchText` runs core's `searchText` for the palette. A new search aborts the one in flight, and `session:logout` aborts it before the token is removed; an aborted search answers `null`, never an error, and the renderer drops it. Closing the palette sends no abort, so its last search finishes unread.
- `issues:list` loads one phase. A new load of a phase aborts the one running for it, and `session:logout` aborts both before the token is removed. An aborted load answers `null`, never an error.
- Page channels: `issues:get` reads one issue with its description and subtasks; `issues:edit` sends a strict `changes` object (assignee, priority, dates, labels to add or remove, parent, Customer, Engagement, original estimate, Time remaining, type); `issues:setStatus` and `issues:setSprint` move by target status and by sprint; `issues:transitions`, `sprints:list`, `users:search` and `fields:options` feed the pickers. Every write refuses an issue outside the settings project through `assertInProject`, a new parent included, and a type change reads the issue first and refuses an Epic or Subtask, as `jm issue edit` does.
- `issues:create` takes a strict object (type, summary, Customer and Engagement ids, and optionally parent, assignee, ADF description, priority, labels, estimate, start date, due date and sprint) and answers `{ key, issue, warning }`. `issues:delete` takes the key, whether to cascade and the subtasks the user was shown, and answers the keys deleted. Both refuse an issue or parent outside the settings project through `assertInProject`.
- `sprints:get` reads one sprint for the Sprint page: `{ id }` in, `{ sprint, issues, stats }` out. See Sprint Page.
- Activity channels: `comments:list|add|edit|delete`, `worklogs:list|add|edit|delete`, `links:list|add|remove` and `attachments:list|add|download`. Ids are digits, bodies and comments are ADF of at most 1 MB, `timeSpent` matches `DURATION_PATTERN`, `started` is an ISO date-time, a file is 1 byte to 100 MB, and no argument carries a path. Every write calls `assertInProject` first; a link calls it for both ends.
- Main rewrites the CLI wording in a core error message before it crosses IPC (`src/main/messages.ts`), so "Run `jm auth login`" reads "Log in again." in the app. The error code and every other word stay as core wrote them, and the CLI never passes through it. It also drops the request a message names ("Jira answered 500 to GET <path>" reads "Jira answered 500"), so no request path reaches the window: toasts, notices and form errors show the short text, and an error shown with Details (`LoadError`, `Failure`, `Reason`) keeps the full text in `IpcError.detail`. `IpcError.status` carries the HTTP status Jira answered with (absent when it did not answer), so `LoadError` can tell a 5xx from a lost connection (`statusOf` in `ipc.ts`). A notice, a create warning or a toast carries only the short text. `core`'s message and `details` are untouched, since the CLI's `--json` output is a public contract.
- `settings:setToggles`, `settings:setDisplay` and `settings:setTreeLevel` write through one promise chain, so two quick presses, or a toggle, a display change and a level, write in order. Each replaces only its own key and keeps the rest of the settings. `setDisplay` takes a strict object: `properties` from core's list of ten, an `order` and a `direction`, an optional `manual` list of issue keys and an optional `widths` map of whole pixels from 1 to 1000.
- `inbox:list` takes nothing and answers `{ issue, unread, change }` per entry. `inbox:markRead` takes an issue key and its `updated` time, and `inbox:markAllRead` the `through` time; both are ISO date-times and answer `null`.
- `views:list`, `views:create`, `views:rename` and `views:delete` take strict objects: a name of at most 80 characters, filters in core's shape (lists of strings, a text string), the three toggles and, on create and update, an optional `display`. Core owns the name rules (trimmed, not empty, unique in any case) and answers `validation_failed` or `not_found`.
- Window focus travels the other way: main sends `window:focus`, and the renderer hands it to TanStack Query's focus manager. Chromium raises `visibilitychange` only when a window hides, so the default would miss a switch back from another app.

## Rules

- Context isolation and the sandbox stay on, and Node integration stays off. The renderer reaches the main process only through `contextBridge` in the preload script.
- The renderer imports only the renderer-safe core entry points: `@jira-mgr/core`, `/issue`, `/hierarchy`, `/adf`, `/timer-calc` and `/view-filter`. Node-only entry points (`/auth`, `/http`, `/search`, `/write`, `/state` and the rest) belong to the main process. `src/shared/ipc.ts` imports the `SavedView` type from `/state` and the `SprintReport` type from `/sprints` with `import type`, which leaves nothing of them in the renderer bundle.
- The main process calls `@jira-mgr/core` and nothing else. Business rules live there. The write guard that refuses an issue outside the settings project is core's `assertInProject`, shared with the CLI.
- electron-vite bundles `@jira-mgr/core`, `zod` and the other `devDependencies`. Dependencies stay external in the main process.
- The package emits CommonJS, not ES modules, so the preload script can run in the sandbox. `electron.vite.config.ts` lists the main entries under `lib`, because `rollupOptions.input` drops the CommonJS and `electron` external settings with Vite 8.
- The e2e entry (`out/main/e2e.js`) is test code built beside the real one. `scripts/package.ts` leaves it out of the app, and fails the package if `e2e.js`, a fake Jira marker or a `require` of anything but `electron` and `node:` built-ins reaches it. Keep every runtime import bundled: the packaged app has no `node_modules`.
- The package is Electron's prebuilt `Electron.app` with `out/` as its app, renamed and signed ad hoc, so it needs no packaging dependency. No code signing identity and no auto-update: the app builds and runs locally.

## Buttons

`styles.css` defines every button once, as classes in the components layer; no component wraps them.

- Two heights: `btn` is 28px (toolbars, forms, dialogs) and `btn btn-sm` is 24px (headers, rows, the sidebar, toasts). `btn-icon` makes either square.
- One control radius, 6px. Popovers and toasts take 8px (`rounded-lg`), dialogs 12px (`rounded-xl`). A chip is a 6px button, not a pill.
- Three tiers: secondary (`btn`, the line border), `btn-primary` (accent fill) and `btn-ghost` (no border, muted text). One disabled style for all: the `--line` fill with `--muted` text.
- Delete is never red at rest. `btn-delete` turns the text red on hover only; `btn-danger`, the solid red fill, belongs to a confirm (the delete dialog and the inline comment, worklog and view confirms). A delete icon is the bin (`TRASH` in `Icon.tsx`) with an accessible name. The two crosses left, a toast's Dismiss and a filter chip's Remove, do not delete data.
- Row actions show on row hover and `:focus-within`, by opacity so keyboard focus still reaches them: a link's bin, Edit and Delete on a comment or worklog, a saved view's rename and bin, a group header's "+".
- A section adds with `AddAction` in its heading: a 24px "+" named "Add link", "Add worklog", "Log work" (Time tracking), "Add sub-issue" or "Attach file".
- Rows of buttons wrap (`flex-wrap`), because a `.btn` neither wraps its text nor shrinks: a dialog's button row must not clip one. The test checks that every button sits inside its dialog.
- The Sprint page's tabs are 24px `btn btn-sm` buttons. The selected tab takes `is-current`, the fill and weight of a lit sidebar item, and no accent border.
- A chrome button never takes `data-row`; the marker is only for row-shaped and bare link buttons.
- The 4px `rounded` that remains (Kbd keycaps, the "Customer differs" badge, the Tree chevron, option and menu rows, the focus ring) is inline decoration, not a control.
- A disabled ghost button fades its text and shows a not-allowed pointer, since it has no fill to lose.
- A picker (`aria-haspopup="listbox"`) is a field, like a select, and a button marked `data-row` fills a row or is a bare text link (subtask rows, menu rows, the summary title). Neither is button chrome, and `e2e/desktop/buttons.test.ts` skips them. It measures every other rendered button: 24 or 28px high, a 6px radius, the `btn` class, no drawn cross, also in Verdana.

## Known Limits

- A new issue shows as read until someone changes or comments on it: a creation writes no changelog history, so nothing names it.
- The Inbox names the newest change by someone else but not how many came after the mark. An issue with over 100 own changes after its mark can hide an older change by someone else.
- A comment is found only when it is the newest comment by creation time, so an edit of an older comment is missed.
- The Inbox has no filter, no snooze and no per-entry "mark unread".
- The Tree shows nothing until a whole phase has loaded, since a partial phase can hold a Story whose Epic is on a later page.
- The renderer cannot cancel a load by itself. A newer load of a phase and logout abort the one running; an unmounted query otherwise runs to the end.
- Filter choices other than statuses, Customers and the fixed lists (Status type, Relations, the date windows) come from the loaded issues, so an issue that is not loaded cannot be filtered for.
- Dates filter by presets around today, with no absolute before and after dates. Relations count a "Blocks" link only while the other issue is not Done.
- Row heights are fixed. A row with a second line would need a rewrite of the window.
- The theme choice lives in `localStorage`, not in the settings file, which the CLI also reads. Move it there if the CLI should honour it.
- Opening the Peek narrows the Tree, which can wrap the toolbar onto another line and, under 700px of Tree width, takes away the 24px column header, so the rows move by the difference. A double-click still opens the issue its first click hit (#201); the wrap itself is not fixed.
- The page cannot clear a parent, since core's `editIssue` takes a key only, and cannot clear the original estimate, since it takes a duration only.
- "Recent assignees" are the people on the most recently updated loaded issues, since Jira keeps no record of who the user assigned to.
- The label list is the labels on the issues loaded so far, so a label used only by a Done issue appears once Done has loaded.
- The optimistic estimate assumes 8 hours to a day and 5 days to a week. A site with other working time shows the difference until Jira answers.
- The create modal has no estimate of its own beyond the original estimate. The images it uploads go in one at a time and the description is written again afterwards, so an issue shows its text before its images. A create that PSAPAC's automation rewrites shows the difference in the notice and does not undo it.
- The second read of a created issue comes once, about 10 s after the create. Automation that lands later is not reported. An edit the user makes to the new issue in that window can be named in the toast as Jira's change. A late read that arrives while an edit of the issue is in flight is not put into the Tree or the page; the edit's own read follows.
- Done children that are not subtasks, of a deleted unresolved Epic, can still show its parent key if the Done phase was still loading when the delete ran, since the delete edits only the lists it holds and the Epic was in a loaded one, so the Done load does not restart. They keep it until Done goes stale (five minutes).
- A subtask added between main's re-read of the subtasks and the delete request still goes with the cascade, since Jira has no conditional delete. The window is one request.
- What Jira does with the children of a deleted Epic (they stay, without a parent) is Jira's documented behaviour and is simulated by the e2e fake. No live PSAPAC delete has checked it.
- Comments, worklogs and attachments load whole: a long thread renders one editor per comment, and a download holds the file in memory. A worklog comment cannot be cleared. Others' comments and worklogs show no Edit or Delete, though Jira lets an admin change them. An image embedded in a comment has not been written to live Jira.
- Description drafts last the session; a crash or quit loses them. Cancelling an edit leaves its uploaded images attached to the issue. A read-only block can be dragged where ADF forbids it, and Jira then refuses the save with its message while the draft stays. There is no link dialog, and nothing inside a table, panel or macro is editable here.
- Subtasks list only on the page, where `getIssue` returns them (each with `done`, from its status category); the Tree builds Subtasks from the parent keys of the loaded issues.
