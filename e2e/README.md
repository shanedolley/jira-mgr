## Run

```
pnpm e2e
```

The command builds the desktop app, then launches `apps/desktop/out/main/e2e.js`, an entry that runs the real app with `fetch` replaced by an in-memory Jira (`src/main/e2e-fake.ts`) and the Keychain replaced by core's own code over a fake `security`. It refuses to start without `JM_STATE_DIR`, and each test gives it a temporary folder, which also holds Electron's own storage. Nothing reaches the network, the real Keychain or the real state folder. The fake holds every write (an edit, a transition or a sprint move) until a test calls `releaseEdit`, so a test sees the optimistic state without a timing window. `releaseNewestEdit` answers the newest held write first, as a network may, and `fieldsOf` (in `harness.ts`) returns an issue's fields as the fake holds them. It answers what the issue page asks: a read of one issue, transitions, assignable users, a board with sprints, and create metadata with Customer, Engagement and priority options. It applies edits as the live project does, so an estimate edit also moves the remaining estimate and Time remaining, and it refuses the summary `reject me` and the priority `Highest`, so a test can watch a rollback. `counts.issueReads` lists each read of one issue and `counts.editBodies` each write received, so a test checks what was sent and that an edit reloaded no list. It creates and deletes issues too. A create holds until `releaseEdit`, stores the description it was sent, answers with the next number from 2000 (clear of `JM_E2E_BULK`'s 1000 to 1999), and applies the PSAPAC automation's rewrite as the handover Traps describe it: every new issue gets the label `PSAPAC` and a 4h original estimate with nothing remaining, and a new Task is also moved to the internal Customer, under `PSAPAC-50`, in Sprint 5, whatever the request asked. It refuses the summary `reject me`, a Subtask with no parent, and a missing Customer or Engagement. A delete holds the same way, refuses an issue with subtasks unless `deleteSubtasks=true`, removes the subtasks with it, leaves the other children of the issue without a parent, and answers 403 for `PSAPAC-3`, so a test can watch a delete roll back. `dropIssue` (in `harness.ts`) removes an issue as if someone else deleted it, so the next refetch loses it. `counts.editBodies` holds a create's request body and, for a delete, `{ delete, deleteSubtasks }`. It also holds the first Done search page until `releaseDone`, so a test sees the Tree before Done issues arrive, and `failDone` makes the next Done page answer 500. `failRead` makes the next read of one issue answer 500, and `failTransitions` the next read of an issue's transitions (the Status picker's lookup). `moveIssue` (in `harness.ts`) changes an issue's status as if someone else did, with no hold and no count, so the next window focus reads it. `counts.doneEarly` counts Done pages requested before the unresolved phase served its last page, which must stay 0. `JM_E2E_BULK=<n>` adds that many open Stories under one Epic, for the virtual window test. `desktop/harness.ts` launches the app and holds these helpers. `launch` returns once the page has loaded, and `readState(stateDir, file)` reads a state file as JSON, or `null` before the app first writes it. Windows open invisible, click-through and without focus, so a run never flashes on your screen, catches your clicks or types into whatever app you are using. (macOS keeps part of every window on a display, so the window cannot sit off-screen.) On Linux without a display, run `xvfb-run --auto-servernum pnpm e2e`. When `CI` is set, the test passes `--no-sandbox` to Electron, because GitHub's runners lack the setuid sandbox helper.

Run on one worker when hunting a flake or running beside other worktrees: `pnpm e2e --workers=1`. Do not write `pnpm e2e -- --workers 1`, which passes the `--` literally and leaves Playwright on its default of 5 workers. Check the worker count in the output. Several worktrees running e2e at once starve Electron and time out `beforeEach`.

Electron's `pnpm install` step downloads its binary. After `pnpm install` in a new worktree, see the Electron check in [AGENTS.md](../AGENTS.md).

`desktop/activity.test.ts` covers D5: the Links, Worklogs, Activity (comments) and Attachments sections of the issue page. PSAPAC-1 holds two comments (one by the signed-in user, one by Other User), two links (it blocks PSAPAC-2, and PSAPAC-3 relates to it) and two attachments (`diagram.png`, `report.xlsx`); PSAPAC-2 holds two worklogs, one of them the user's; PSAPAC-4 has a 2h estimate and nothing else. The fake answers `GET` and `POST /issue/{key}/comment` and `PUT` and `DELETE .../comment/{id}`; the same for `/worklog` (`adjustEstimate=auto` moves the remaining estimate and Time remaining (h), as the live rule does); `GET /issueLinkType` (eight types, the first five being Q19's), `GET /issue/{key}?fields=issuelinks`, `POST /issueLink` and `GET` and `DELETE /issueLink/{id}`. A link keeps the blocker as its `inwardIssue`, as Jira does. Every write holds until `releaseEdit`, is counted in `counts.edits` and recorded in `counts.editBodies` (as `{ comment: 'add' | 'edit' | 'delete', ... }`, `{ worklog: ..., adjustEstimate, ... }` and `{ link: 'add' | 'remove', ... }`), and `refuseNextEdit` makes the next one answer 400. A download opens a stand-in for the native save dialog, which records the offered name in `counts.downloads` and writes under `<JM_STATE_DIR>/downloads/`; `cancelNextDownload` (in `harness.ts`) makes it answer "cancelled". Drops are `DragEvent`s with a `File`, dispatched on `[data-drop-zone="Attach file to issue"]`, on the description's zone, or on the properties sidebar for a drop outside both zones. An upload is held until `releaseUpload`, like D4's. Four helpers in `harness.ts` act as another user or hold a read: `setComment(app, key, id, adf)` changes a comment and `removeComment(app, key, id)` deletes one, with no hold and no count; `addWorklog(app, key, comment)` adds a worklog by the signed-in user whose comment is the given document (an empty document, or media only), before the page opens; `holdReads` holds every comment and link list read until `releaseReads`, so a rollback test sees the page before the refetch on settle can put a row back.

`desktop/buttons.test.ts` covers the button system: every rendered button with chrome is 24 or 28px high with a 6px radius, on the login screen, the list, the Peek, the page, its forms and confirms, the dialogs and a toast, also in Verdana; dialogs take 12px and menus and toasts 8px; a disabled button is the line fill; the section headings add with a 24px "+"; a delete is a bin that shows on row hover or focus and is red only on hover; no delete draws a cross.

`desktop/surfaces.test.ts` covers the dialog scrim and shadow (the light backdrop's computed alpha is below the dark one's), the drop zone (no text stays legible under a label: the zone's content fades and the label's surface covers it) and the login screen (the mark, the Keychain hint, a 400px form on `--canvas`).

`desktop/timer.test.ts` covers D9. It starts the app on a scratch `JM_STATE_DIR` and drives the timer through `T`, the issue page button and the sidebar's Stop button. Because the app and `jm` share `timer.json`, a test sets up a timer that began hours ago by writing that file, as `jm timer start` would, and the app shows it within its 5 second poll. The groups are start and stop (the row, page and sidebar clocks; the stop dialog's Log, Discard, Cancel and Esc; an Epic refused), switch (the old worklog is written before the new timer starts; Discard; a timer `jm` changed meanwhile is refused), the long timer (a 9 hour timer warns, needs "Confirm and log" or an edited time), and reminders. A worklog write holds until `releaseEdit`, like any write. A reminder is a stand-in for the native notification: the e2e entry records `{ title, body }` in `counts.notifications`, and `JM_E2E_REMINDER_MS` sets how often the app looks at the timer (30 s otherwise). The test that closes the window runs on macOS only, where the app outlives its last window. The suite launches Electron with `TZ` set to an `Etc/GMT` zone where the local time is about noon, because the tests start timers 1 to 9 hours back and core flags a timer that crosses local midnight.

`desktop/inbox.test.ts` covers the Inbox page, its sidebar badge and `inbox.json`. The fake answers the Inbox's search (any JQL with `currentUser()`), `GET /issue/{key}/changelog` and the newest-comment read (`orderBy=-created`); none counts as a Tree search or an issue read. Three helpers in `harness.ts` act as a user: `inboxChange(app, key, 'me' | 'other', items)` records a changelog history and moves the issue's `updated` on, `inboxComment(app, key, 'me' | 'other')` adds a comment the same way, and `inboxWatch(app, key)` lists an issue with no change. An issue is in the Inbox search only once one of them has touched it. Their times are within the last hour by the real clock, because the Inbox forgets read marks older than 14 days. `counts.inbox.searches` and `counts.inbox.reads` show how often the app asked Jira. The poll test installs Playwright's page clock before login and fast-forwards five minutes.
