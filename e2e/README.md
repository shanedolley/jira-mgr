# End-to-End Tests

Playwright tests that cross package boundaries. Unit and integration tests sit beside the code they test.

| Suite      | Drives                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `desktop/` | The built desktop app, through Playwright's Electron driver, on a fake Jira and a fake Keychain: `shell.test.ts`, `tree.test.ts`, `page.test.ts`, `create.test.ts`, `delete.test.ts`, `keyboard.test.ts`, `properties.test.ts`, `editor.test.ts`, `avatars.test.ts`, `activity.test.ts`, `views.test.ts`, `display.test.ts`, `filters.test.ts`, `lateRead.test.ts`, `package.test.ts`, `timer.test.ts`, `surfaces.test.ts`, `textSearch.test.ts`, `actions.test.ts`, `palette.test.ts`, `toast.test.ts`, `buttons.test.ts`, `subtasks.test.ts`, `inbox.test.ts`, `sprint.test.ts`, `blocked.test.ts`, `overviews.test.ts`, `narrow.test.ts`, `bulk.test.ts`, `timetracking.test.ts`, `contextmenu.test.ts`, `manual.test.ts`, `timeprops.test.ts`, `holdfade.test.ts`, `logwork.test.ts`, `summary.test.ts`, `estimate.test.ts`, `cell.test.ts`, `slots.test.ts`, `labels.test.ts` |

## Run

```
pnpm e2e
```

The command builds the desktop app, then launches `apps/desktop/out/main/e2e.js`, an entry that runs the real app with `fetch` replaced by an in-memory Jira (`src/main/e2e-fake.ts`) and the Keychain replaced by core's own code over a fake `security`. It refuses to start without `JM_STATE_DIR`, and each test gives it a temporary folder, which also holds Electron's own storage. Nothing reaches the network, the real Keychain or the real state folder. The fake holds every write (an edit, a transition or a sprint move) until a test calls `releaseEdit`, so a test sees the optimistic state without a timing window. `releaseNewestEdit` answers the newest held write first, as a network may, and `fieldsOf` (in `harness.ts`) returns an issue's fields as the fake holds them. It answers what the issue page asks: a read of one issue, transitions, assignable users, a board with sprints, and create metadata with Customer, Engagement and priority options. It applies edits as the live project does, so an estimate edit also moves the remaining estimate and Time remaining, and it refuses the summary `reject me` and the priority `Highest`, so a test can watch a rollback. `counts.issueReads` lists each read of one issue and `counts.editBodies` each write received, so a test checks what was sent and that an edit reloaded no list. It creates and deletes issues too. It serves Jira's bulk endpoints too: `GET /bulk/issues/transition` (the transitions common to the issues asked about), `POST /bulk/issues/transition` and `POST /bulk/issues/fields` (priority, assignee, added labels, Customer and Engagement), each answering a task id, and `GET /bulk/queue/{taskId}`, which answers COMPLETE with the issue ids processed and the ones failed. Bulk calls are not held, and `counts.bulk` lists each POST with its body. `refuseNextBulk` makes the next bulk POST answer 400, so core runs the batch one issue at a time through the held single writes, and `refuseKeys` makes every write to chosen issues fail, in a bulk task as a failed issue and singly as a 400. A create holds until `releaseEdit`, stores the description it was sent, answers with the next number from 2000 (clear of `JM_E2E_BULK`'s 1000 to 1999), and applies the PSAPAC automation's rewrite as the handover Traps describe it: every new issue gets the label `PSAPAC` and a 4h original estimate with nothing remaining, and a new Task is also moved to the internal Customer, under `PSAPAC-50`, in Sprint 5, whatever the request asked. It refuses the summary `reject me`, and for the summary `lose reply` it makes the issue and then answers 500, as a lost response looks to the app. It also refuses a Subtask with no parent, and a missing Customer or Engagement. A delete holds the same way, refuses an issue with subtasks unless `deleteSubtasks=true`, removes the subtasks with it, leaves the other children of the issue without a parent, and answers 403 for `PSAPAC-3`, so a test can watch a delete roll back. `dropIssue` (in `harness.ts`) removes an issue as if someone else deleted it, so the next refetch loses it. `counts.editBodies` holds a create's request body and, for a delete, `{ delete, deleteSubtasks }`. It also holds the first Done search page until `releaseDone`, so a test sees the Tree before Done issues arrive, and `failDone` makes the next Done page answer 500. `holdUnresolved` (with `releaseUnresolved`) holds the open-issues search and `failUnresolved` makes its next page answer 500, both set before login. `failRead` makes the next read of one issue answer 500, and `failTransitions` the next read of an issue's transitions (the Status picker's lookup). `moveIssue` (in `harness.ts`) changes an issue's status as if someone else did, with no hold and no count, so the next window focus reads it. `counts.doneEarly` counts Done pages requested before the unresolved phase served its last page, which must stay 0. `JM_E2E_BULK=<n>` adds that many open Stories under one Epic, for the virtual window test. `desktop/harness.ts` launches the app and holds these helpers. `launch` returns once the page has loaded, and `readState(stateDir, file)` reads a state file as JSON, or `null` before the app first writes it. Windows open invisible, click-through and without focus, so a run never flashes on your screen, catches your clicks or types into whatever app you are using. (macOS keeps part of every window on a display, so the window cannot sit off-screen.) On Linux, `launch` starts one Xvfb per worker and runs that worker's apps on it, so workers never share an X clipboard, and `pnpm e2e` needs Xvfb installed but no `xvfb-run`. When `CI` is set, the test passes `--no-sandbox` to Electron, because GitHub's runners lack the setuid sandbox helper.

Run on one worker when hunting a flake or running beside other worktrees: `pnpm e2e --workers=1`. Do not write `pnpm e2e -- --workers 1`, which passes the `--` literally and leaves Playwright on its default of 5 workers. Check the worker count in the output. Several worktrees running e2e at once starve Electron and time out `beforeEach`.

`pnpm install` leaves Electron without its binary, which Electron downloads on first use. Parallel workers that each start that download break each other's launch, so run `pnpm --filter @jira-mgr/e2e exec install-electron` before `pnpm e2e` when the dist is missing. After `pnpm install` in a new worktree, see the Electron check in [AGENTS.md](../AGENTS.md).
